# Cricket Props Hub: the free stats site (`site/`)

A free player-props and fancy-markets stats site built on this repo's data. Static pages plus two small serverless functions
(`/api/ask`, `/api/live`), hosted on **Vercel Hobby**. Optional free Supabase Auth for server-side Saved. Nothing paid required, no model hosting.

## What it does
| Page | What you get |
|---|---|
| Home / **Ask** | Type a question in your own words (typos fine). A free Gemini model turns it into a *query plan*; the site runs that plan on the real data and shows the answer, the filters used, the sample size and the data freshness. |
| **Fixtures** | Upcoming internationals/leagues from `data/fixtures/upcoming.csv` only. The bookmaker feed is for odds, never for fixtures or start times (books serve different regions). Live scores (team totals, current batters/bowler, and player so-far vs booked lines) refresh about every 15 seconds from the Source A schedule, match and scorecard pages, **only for matches we have player-prop or fancy odds for**; they are never used to settle a prop. Props and Match Fancy tabs (and unpriced fancy markets) stay hidden when that match has no bookmaker line. |
| **Players** | Runs, balls, 4s, 6s, wickets, runs conceded. Hit rate over/under any line, a ladder of lines, median/mean, last-N form, fair decimal odds, split by opposition, venue, home/away/neutral, batting first/chasing, batting position, year and competition. One format at a time, never mixed. |
| **Teams & grounds** | Match totals and fancy markets: match 4s/6s, 30s, 50s, 100s, double-digit and single-digit scores, ducks, extras, run-outs, highest over, most runs conceded / most wickets by a bowler, top score, first over and first-N-overs session runs, team markets (a side's own innings), and who tops the batting card. One singular ground page powers `/venue/:id` and `/fixture/:id/ground` (fixture entry keeps a tour chip + back to the match). Search (⌘K and the venues list) matches grounds as well as players and teams. The page is player-page shaped: pin mark + ground/city hero, Matches / Weather / Local metrics from free Open-Meteo, T20/ODI/… format chips (no All — one format at a time for matches and markets) beside a Filters button (AdjustmentsHorizontal + Men/Women/All for gender, same pattern as Match Fancy’s L20), FixtureCards, then Markets (Match Fancy shape: median/mean/range, bars, O/U, line ladder — not the Ask ResultView card) — no match scorecard or live board. Completed cards show the match date (“11 Sep” in the current year). Old `/venue/<idx>/preview` links redirect to `/venue/<idx>`. |
| **Leagues** | `/leagues` (tab bar and sidebar): a picker of leagues, live ones and those about to start first with Big Bash on top, then that league's season stats and trends. See "Tournament stats" below. |
| **Competitions** | A league or series (`/league/<event idx>`, every league in the data is listed on `/competitions`): a **Stats** tab first (the season's top run-scorer, wicket-taker and a third leader, then lists for batting, bowling and overall, and the same measures season by season), then Markets, Teams and Results. See "Tournament stats" below. |
| **Partnerships** | For any two batters: who is dismissed first, stand sizes, split by format, opposition and venue; opening pair only if you like. |
| **Prop Hunter** | The best-value props for upcoming matches from `value_bets/out/value_bets_latest.json`, read live from GitHub (falls back to the snapshot built into the site). |
| **Privacy / Terms / Docs** | Unlisted legal pages (`/privacy-policy`, `/terms-of-use`, `/docs`): what the site stores, that it is cricket stats and data, and that it does not offer, promote or encourage gambling. Not in the chrome, sitemap or search index; they load only if the URL is typed. `/privacy`, `/terms`, `/disclaimer` and `/responsible` redirect to those paths. |

See [SITE_MAP.md](SITE_MAP.md) for the page-by-page comparison with StatsHub.

## How the numbers are produced
```
Base all_json.zip ─┐
data/provisional/*.json ─┼─► python -m cricket_site.build ─► site/public/data/*.json ─► browser engine (site/packages/engine)
data/fixtures, value_bets ┘                                                              ▲
                                                question ─► /api/ask (Gemini) ─► plan ───┘  (validated, then run on the rows)
                                                Source A schedule + match + scorecard ─► /api/live (15 s cache) ─► fixture scores + live board + player so-far + fancy so-far + each priced player line settled (value, final, Cleared / Missed / Push, Not in XI)
```
* **Builder** (`src/cricket_site`, stdlib only): parses the ball-by-ball JSON into per-innings batting rows (position, innings order,
  runs/balls/4s/6s, dismissal), bowling spells, partnerships (who was out, runs, balls, opening flag) and match-market aggregates.
  Provisional (scraped) matches are added as player-total rows when Base does not have the fixture yet (same dedupe as
  `cricket-data query`: same teams, +/-1 day) and only when `link-players` gave the player a Base id.
  Output is ~35 MB of JSON (~12 MB compressed): `meta.json`, `index.json`, `matches.json`, 64 player shards `p/NN.json`, `fixtures.json`, `props.json`.
  I checked ~71,000 player rows against `data/players`: every difference was a super-over (the site ignores super overs on purpose).
* **Engine** (`site/packages/engine`, no dependencies, runs in the browser and in node): filters, hit rates, fair odds, markets, partnerships,
  name resolution with typo tolerance, the plan runner, and live-score parsing (`live.js`). **Every number on a page is computed here from the rows
  or from the live snapshot** — never from the LLM.
* **The model never supplies a number.** `/api/ask` (`site/api/ask.js`) sends only the question text to Gemini with a fixed instruction and gets
  back JSON, which `sanitizePlan` reduces to whitelisted fields. The plan is then resolved against the real player/team/venue tables and executed
  in the browser. If the key is missing, rate-limited or the reply is unusable, the built-in rule parser (`engine/nl.js`) answers instead.
* **Live scores.** `/api/live` (`site/api/live.js`) reads Source A's schedule, match and scorecard pages (no key; Source B is not used, its cards lagged its own header), caches ~15 seconds, and returns compact team
  scores plus batting/bowling so-far **only for matches in the book feed** (player props, event markets, or fancy). The fixture header shows a
  live board, a compact strip so the tabs and the first props stay on the first phone screen (the pair side by side with a small avatar, name with runs/balls under it; one bowler line; the ball-by-ball tape with a divider at the over break). The partnership is the source's stand when that figure fits this innings; a negative chase margin is dropped, and the stand is then the innings total (no wicket down) or the innings minus the last fall
  of wickets. The fixture page uses one match header for upcoming, live and completed games. It holds the status, venue, teams and their scores when available. In play it also holds the live strip. **Full scorecard** expands the innings tables inline when innings data exists, with partnership, last wicket and run rates during play. Existing `/fixture/:id/scorecard` links still open the standalone view. The top bar keeps the back button, live-feed mark and Share through `HeaderActions`. There is no Scorecard chip. The chips are Props, Match Fancy, **Ground** (rendered in the page with a "Full page" link to `/fixture/:id/ground`), Form (only when a side has games in this format), Grid and Custom line.  The live strip has player photos; the scorecard tables have none. Scorecard has batting (how-out, R, B, 4s, 6s, SR), extras, fall of wickets, yet to bat, and bowling (O, M, R, W, Econ) — the
  same columns Source A and Source B show. Games with no odds stay off
  the rail and off the live snapshot. The schedule page (cached ~5 min) lists the games and their URLs; scores, the current pair and rates come from the **match** page
  and the full card from **match-scorecard** (`getSC4`; `max-age` 10 s, robots-allowed; we do not call `$LIVE_SOURCE_BASE/api`), so a chase shows the chasing side's pair the moment it starts.
  The browser polls that route.
  **Playing XI.** The card lists a side's eleven (batters plus yet to bat) as soon as it is down to bat, so a prop row shows **Not in XI** and is dimmed when that side's eleven are all known and the player is not one of them. The other side stays unmarked until it has batted: the source only gives its XI through an app API we do not call. Pages are fetched from 90 minutes before the start so the batting side's XI is picked up at the toss. A priced match also stays in Hot props, with its last pre-match prices, for 24 hours after the start (6 days for a Test) and while the live feed still lists it as being played.
  Unofficial and can change. Every priced player line of a match is settled here (`lines` on each match: value, state, verdict, Not in XI), by the player's id through the identity table, so the browser does no matching of its own; while the match is on these are "so far", and a final number in a finished match is its result, stored in the archive (`docs/PROJECT_GUIDE.md` 5.4c). VOID/DNP rules still apply: a player with no row has no result. Fancy so-far is the same 15 s snapshot, read in the browser (`fancyStanding` in `live.js`: innings totals via `liveMarket`, then `lineVerdict`): Match Fancy, the Fancy cards and the home Props snippet overlay it at view time, so a 10-minute scored history does not freeze the live number. A so-far or a decimal price that moved flashes green or red, same words as a player prop (N so far / Cleared / Missed / Push). A fancy side run line tagged `bat_first` (6/10/15/20 over session, or the full innings) shows VOID once that side is bowling first; premium fours / sixes are not tagged and stay live for both.
  Kick-off, "today / tomorrow" and countdowns stay in the **viewer's time zone** (`site/src/lib/format.ts`).

## Cadence and what we show
A priced match stays on the site for **24 hours after kick-off (6 days for a Test / first-class; a Test with a result goes 24 hours after it ended)**, as one match, with the last **pre-match** prices plus live so-far. The UI never pretends we have moving in-play odds.

| Job | When | What it is |
|---|---|---|
| Odds / book lines | Hourly, **round the clock** (`value-bets.yml` `30 * * * *` UTC). Feed G / Feed H go through free Mumbai hops (Vercel bom1 / Cloudflare Worker), not a paid VPS. | Closing pre-match player props and fancy only, for matches starting in the next **10 days** when a book has prices (`FEED*_HORIZON_HOURS`). Value-bet alerts use the next **7 days** (`WINDOW_HOURS`). Every adapter and `book_lines` drop `in_play`. After the first ball the next pull would empty the match; `carry_started` copies yesterday's closing prices for 40 h (T20/ODI) / 6 days (Test), a Test with a result goes a day after it ended instead, and a Test's morning restamp of `start_utc` is merged onto the first morning so the file is not three SA vs AUS clones. |
| Live scores / so-far / Cleared | `/api/live`, ~15 s, Source A pages, **books-priced matches only** | The in-play layer we do have: team scores, player so-far, fancy so-far (`fancyStanding`), and every priced player line settled on the server. |
| Archive results | Same hourly value-bets job, `--results` against `/api/live` | Finished numbers stored on the match's archive file. |
| Fixtures scrape | Every 30 minutes (`scraper-update.yml` `7,37 * * * *`) | `upcoming.csv` for the rail and `/api/live` gap rows. |
| Site data deploy | Hourly at `:50` plus push to `site/` (`site.yml`) | Bundled `lines.json` can lag the GitHub `book_lines.json` the browser also fetches (1.5 s). |
| Ball-by-ball / Base | Daily 05:30 UTC | Not used for live props. |

The book pull runs every hour of the day, so a match starting at any hour has its closing line pulled within the hour before it starts. The site keeps the carried closing line and the 15 s scorecard.

**Test (and T20) line types.** Books do not price "3rd innings" / "4th innings" as match innings for a player. `inn` is the player's **own side's** 1st or 2nd innings. Unscoped (`inn` 0 / absent) is the whole Test (both innings summed). Show match totals and 1st / 2nd innings of *his side* when a book listed them pre-match; never in-play ladders around the current score, never 3rd/4th match innings. After the start: frozen line + so-far / Cleared / Missed / Push / Not in XI. Fancy **team** innings lines (`inn` 1 or 2 on a team total) are scored on that side's own 1st/2nd innings and shown as their own rows on Match Fancy and the Fancy cards (a live Test often has only those left after match totals come off). They are never mixed with the match total. Live tracking is the same 15 s poll as player props (`fancyStanding`): a side's own innings is `final` once that turn is over (a later card innings with batters/totals, or all out — not an XI-only stub); a limited-overs team total is `final` with that innings; a Test match total and a whole-match market stay live until the match ends. A `bat_first` session or lambi voids once that side is bowling first (premium fours / sixes are not tagged).

The keep window (`keepMsFor` / `sameMatchWindow` in `site/packages/engine/lines.js`) is the only clock Hot props, the player page, `/api/live` matching and the rail's finished list share. A Test that has a result is let go earlier by the published data, not by the browser: `carry_started` stops carrying its lines in `book_lines.json` (the file Hot props and its match chips are built from) at its end + 24 hours, and `build_fixtures` stops listing its schedule row then (`cricket_site.testend`, `_drop_ended_tests`), so an app in the wild needs no update. The end is `settled_at` in its archive file (the hourly run that first saw the result, so up to an hour late), never later than the start of day 5. The fixture page opens from the archive, with its lines and results. A Test with no result yet keeps the 6 days. The home list's extra "quiet day" filler (up to 4 days of finished limited-overs matches when fewer than three games are lined up) is display-only so the rail is not bare.

## Settlement rules and definitions
* T20 summary markets are void unless both innings reach 80% of the scheduled balls (96 of 120) or ended naturally (all out; the chase reached its target, with no DLS-style adjustment); ODI likewise (240 of 300); The Hundred 80 of 100; T10 48 of 60; 60-over 288 of 360.
  Tests: void unless there is a result, or 300 overs (5-day) / 200 overs (4-day) were bowled. Void matches are left out of match/team markets.
* 30s = 30-49, 50s = 50-99, 100s = 100+, double-digit = 10+, single-digit = 1-9 (ducks excluded). Team markets count only the team batting first.
* Retired hurt is not a wicket. Penalty runs count. Runs conceded = batter runs + wides + no-balls + penalty (as in `data/players`). Super overs are ignored.
* Formats: T20 = T20 + T20I, ODI = ODI + 50-over List A, Test = Tests only, **The Hundred / T10 / 60-over are their own formats**. A T20 in a Test series must not price the Test. First-class (`MDM`) is not included.
* Fair decimal odds = 1 / hit rate on the filtered sample (pushes on whole-number lines are void). Decimal odds only.
* Home/away/neutral is *inferred*, because Base has no home flag: the event ("X tour of Y"), the venue's tour history, its country in
  `value_bets/mappings/venue_geo.csv`, then the team that plays at least half of the venue's internationals. Unknown hosts are left out of home/away filters.

## Player screen (app-style UI)
The player page (`/player/<idx>`) is `site/src/pages/Player.tsx`: a sticky app bar on phones, a prop rail of every player-prop category (runs, balls, fours, sixes, wickets, runs conceded, balls bowled, player performance). Stats a book prices for this player on the nearest match (`bookStatsFor`) sit at full weight; the rest are muted. Opening an unpriced category still shows the usual chart, look-back pills and fair decimal price from history, with a status under the metrics: “No book is offering odds for {stat} on this match” (the line is a research median, labelled as such, never a listed market). A hero (photo, name, round buttons), a format switch, one tappable bar chart with Over/Under, a line stepper and look-back pills that show each window's hit rate (`engine/windows.js`, unit-tested by hand-computed numbers), a bottom sheet for filters and for a tapped game, and Lines / Game log / Splits tabs. **Match-side kit and crest:** the hero shirt, team name, crest and the crest/flag on Hot props rows follow the side the books (or the schedule) file him under for that match (`matchSide` in `engine/next-match.js`: India vs NZ → India kit and flag; IPL → Sunrisers crest and kit); with no match they stay on his profile team. The share/OG card uses the same book-line team for the shirt. **Which match when two are priced:** ODI and List A share a format, so a Black Cap can have a club Ford Trophy line and a New Zealand ODI line open at once. A prop row / fixture link carries `?line=` and `?start=` (the kick-off); `ofBookMatch` / `pickPricedMatch` / `bookLinesFor` prefer that match over the chronologically sooner club game, write `start` into the URL once chosen, and keep kit, lines and the next-match card on it when the prop category changes (a format change clears `start`). With no prefer, the soonest booked match in the keep window still wins. **Desktop (`lg+`)** is a 12-column board, not a stretched phone column: a compact metrics strip, then the chart first (8) beside the booked lines (4), then the this-match card (5) under the chart. Look-back pills sit under the bars. Ground vs opponent hit rates sit as two cards inside the match block. On a phone it is still one column (metrics, chart, this-match, lines). The **next match** card (`components/app/next-match.tsx`) is that preferred booked match still in the keep window (24 hours after the start, 6 days for a Test — the same window Hot props uses), including one that is in play or just finished: both sides and the ground; the books' decimal over/under on the line the chart is on; and, once the match has started, where that line stands (`lineStanding`: so far / N to go / final / Cleared / Missed / Push, the same words as Hot props). A so-far or a book's price that just moved flashes green or red with an arrow (`Tick`, from the 15 s live poll — there is no websocket). How often he has cleared that line at that ground and against that opponent (the same chart entries, this format; DNP/VOID out) sits under the prices, each with a fair decimal price (`engine/next-match.js`). The heading is "This match" while it is live or finished. A finished listed match is not replaced by the schedule's next unpriced game, so the page does not say "No props live yet" while Hot props still has her. With no booked line for this stat it says no book is offering it, and still charts form on a median line (`suggestLines`) rather than hiding the category. Prop-category chips (`bookStatsFor`) use that same keep window, and two books that stamp the same fixture minutes apart are one match (a sixes line is not dropped because another feed listed player performance 30 minutes earlier). An explicit `?stat=` in the link is kept. The chart keeps the line and side in the URL with `replaceState`, so a page can be shared. UI library: shadcn/ui (Radix) with Motion for animation; see PROJECT_GUIDE 5.3.

**Bookmaker lines.** The value-bets pipeline saves every matched two-sided player line (runs, sixes, fours, wickets; decimal over/under per book) to `value_bets/out/book_lines.json` (`src/value_bets/booklines.py`, matched to Base player ids). The site builder bundles it as `data/lines.json`, and the player page reads the live file from GitHub (falling back to the bundle). For a player with a priced upcoming match, the chart opens on the market's **main line** (the one priced closest to evens, `engine/lines.js`) instead of the median-based default, and a "Bookmaker lines" card shows each book's prices, the no-margin market probability and his own hit rate over each line; tap a line to put it on the chart. Players or stats with no market line still chart form on a median line (floor(median) + 0.5, `suggestLines`) so you can look at history. The next-match card says no listed odds (no book is offering that stat) and still shows ground / opponent hit rates on that research line; it never treats the median as a listed price. Books rarely quote the same line for a player and stat, so a Hot props / fixture Props row lists each book's own line and over price under the row (`bookQuotes` in `engine/lines.js`; `BookQuotes` in `hot-props.tsx`). A **single book still shows its mark and price on the third row of the prop card**, same place as when several books quote; the "+N books" toggle appears only when another book is quoting. With 2+ books the lowest line, and the best price at it, is in the accent colour. The row's edge, hit rates and bars stay on the main line. The ground chip uses a short stadium name (`shortVenue` in `lib/format.ts`: WACA, MCG, Wankhede), with the full venue on the title. On the phone prop card the bookmaker mark is row 3; **N in L10** and **hits/played at the ground** sit on row 4 with the form bars (EDGE stays top-right). Fancy rows (`OverviewRow`) do the same: the book's mark sits next to the price even when it is the only book; `BookTable` is only the extras. Every place a book's price appears (those rows, the player page's lines, the fancy cards, and the share/OG card next to the decimal price) marks the book with `BookBadge` / `bookLogoStem` (`components/app/book-badge.tsx`, `packages/engine/books.js`): one stem per file in `site/public/books/` (bet365, Ladbrokes, LeoVegas, FairWin247, Dafabet, Reddybook, Polymarket), matched from any feed name the books publish (`Ladbrokes`, `FairWin247 Premium`, `moviodds_bet365`, …). The mark is as the site owner supplied it, cropped or scaled and never redrawn; the site is dark, so a white or reversed version is best. A book with no file shows a plain name chip; a logo that fails to load falls back to the name. The About page and the terms page say the names and logos are their owners' trademarks, shown only to say where a price comes from.

**Edge.** The EDGE figure on Hot props, the player page's best-price line and Match Fancy is `shrunk chance x best price - 1` (`sideEdge` in `site/packages/engine/stats.js`, unit-tested by hand-computed numbers). The hit rate is the window shown (L5 / L10 / L20 / L30 / All; the season and head-to-head windows on Hot props), over the games he played. It is pulled toward the market's no-vig chance of that side, `(hits + 10 x market) / (played + 10)`, so the market counts as ten extra games: 8 of 10 against an even market is 0.65, not 0.80, and 40 of 60 is 0.643, not 0.667. The price is the best any book offers for the side, and no edge is shown under ten played games. At 1.90 / 1.90 a record that matches the market gives -5%, the books' margin. It is a measure of expected profit per unit, not a stake size or a promise: nothing here models the matchup, ground or conditions except through the market's price (the hourly pipeline's context model is not used by the site yet). Match Fancy's rows are scored by `site/packages/engine/fancy-edge.js` (`marketRow` / `fancyOverview`; `match-fancy.tsx` only adds labels and ids), the same code the Telegram fancy edge alerts use, so a channel alert and the tab show the same number (docs/OPERATIONS.md, "Fancy edge alerts").

**Innings scope (Tests).** For a Test batter the books price the match total and his side's first innings (`inn` on the line, `docs/VALUE_BETS.md`), and the page has a three-way **Both innings / 1st innings / 2nd innings** switch (`?scope=0|1|2`, shown for every Test batting stat, a scope with no priced line still charts that innings; the sheet's "batted first / chasing" filter is a separate thing). The switch picks the lines (`bookLinesFor(..., inn)` gives one scope at a time, `bookScopesFor` lists what is priced) and the chart: a first-innings line is charted against what he made in his side's first innings of each Test only (`filters.tinn`, from `store.teamInningNo`: his side's own n-th turn, not the match's n-th innings; the plan field is `team_innings`), never against match totals. With no `scope` in the link the page opens on the match total when it is priced, else on the first scope that is. The Hot props list gives a first-innings line a row of its own, tagged with its scope.

**Props are never deleted.** A fixture that has arrived and been priced keeps its props: the list on the home page lets a finished match go after a day (`shownFixtures`), but the fixture's own page (`/fixture/<id>`) always works. When the schedule no longer lists the match, or the live book file has let its lines go, the page reads the match's archive file (`value_bets/archive/YYYY-MM/<fixture id>.json`, see `docs/VALUE_BETS.md`) through `useFixtureBooks` (`src/hooks/useEngine.ts`, `loadArchive` in `src/lib/feeds.ts`; the id is checked against the fixture-id pattern before it becomes a URL). `archiveFixture` rebuilds the fixture from the file and `withArchive` adds its lines to the book doc (`site/packages/engine/lines.js`, unit-tested); the props list scores them from the player's history like any others, and shows each result from the file's `results` (stored by the server once the match was over, `docs/VALUE_BETS.md`), else from the data once the match is in it.

**Home rail order, and settings that need no deploy.** The rail (`src/lib/priority.ts`) clusters by series (`arrangeFixtures`): matches in play lead, then those starting within 24 hours (still to come, then finished, newest first), then later games of that series up to 10 days. Series with a match in play lead; among the rest a kick-off in the next 24 hours leads a bigger match later in the week, with a lift for the viewer's own team (read from the time zone, then the language), their part of the world and the big tournaments. A just-finished T20 stays next to that series' next game instead of falling behind every other upcoming card. Finished limited-overs matches stay 24 hours from the start (`shownFixtures` / `keepFinished`; a Test keeps 6 days). On a quiet day, finished limited-overs matches can stay up to 4 days so the rail is not bare. The knobs are published as `config/home_rail.json` and read at view time (`loadRail` in `src/lib/feeds.ts`, `useRail`), so changing one is a commit to that file on `main`, live in about 5 minutes (the raw-file cache), with no site build: `tiers` (group order), `bonus` (`home`, `homeWomen`, `region`, `event`), `bigEvent` (whole words looked for in the series name), `standing` (a team key such as `southafrica` to a number) and `region` (a team key to its part of the world). Anything missing or mistyped keeps the built-in value (`sanitizeRail` reads only these keys, with limits), and a test keeps the file equal to the built-in settings, so edit both when a built-in default is meant to change.

**Caching of the data files (so a returning visitor asks for almost nothing).** Every `.json` under `/data` except `meta.json` has a content hash in the built page (`window.__DV`, made by `scripts/data-manifest.mjs` in the Vite build) and is fetched as `/data/<file>?v=<hash>` (`dataUrl`, `src/lib/data-url.ts`; the engine's `createStore` takes it as `urlFor`). `vercel.json` serves a URL with `v` as `private, max-age=31536000, immutable` and one without it as `private, max-age=120` (the two rules exclude each other with `has` / `missing`). A file's URL changes exactly when its bytes do, so an hourly deploy that did not touch `matches.json` or a player file gives a returning browser no request for it at all; `private` keeps the Edge gate in front of the first fetch (the gate cookie and `X-Cd-K` are still checked on a cache miss). Old clients and the app read the plain URLs, which stay valid. The page head also starts `/api/gate` before the app's scripts run (`headScript`), and `gateKey` uses that answer once, so the first visit no longer waits for the scripts before it asks for the cookie. `/books/*` logos are kept a day. No service worker on purpose: versioned URLs give the same repeat-visit win without an update path that can pin a stale shell.

**How the home page loads (what shows when).** The shell renders once the player index is in. `matches.json` (the match history) keeps downloading and joins the store on `store.ready`; home does not wait for it, and any other page holds its skeleton until it has (`HistoryGate`). The three feeds the rail reads (the book lines, `config/home_rail.json`, `/api/live`) are started in `main.tsx` before the data files finish (`prefetchFeeds`, `src/lib/queries.ts`), not when the page mounts. `/fancy`, `/props` and a fixture page prefetch `/api/live` the same way (the rail file stays home-only). `loadLines` fetches the bundled `lines.json` and the live file together and keeps the newer by `generated_at_utc`; the live file is given up on after 1.5 s. The rail (`useHomeRail`) shows a skeleton until the schedule and the lines are in, so it is never the unpriced schedule that the priced list then replaces. Matches in play lead the rail, so the live state has to be there for the first paint: the last `/api/live` body is kept on the device for 30 minutes (`src/lib/live-cache.ts`) and is the live query's starting point (stale, so the fresh body is asked for at once), which puts live matches in front on the first paint of a revisit. With no kept body the rail waits up to 1.2 s for the live scores (0.8 s for the rail file) and then paints with what it has. A fresh body that changes a match's state (gone live, ended) re-sorts the rail; one that changes nothing leaves it as it was. **Hot props** score the selected day's lines (`hotLines`, `src/lib/hot-lines.ts`; tomorrow is its own query, run when asked for; a fixture page scores only its own match). A match that has already started and is still in the keep window — 24 hours, 6 days for a Test, because the books restamp a Test each morning — is today's, so day 4 of a Test is not dropped because its first start was earlier in the week. Player files for matches that have already started are fetched first, that first file on its own, and its rows are shown as they are scored. The rest of the day's files then come eight at a time. Rows of a match in play come first, then the higher hit rate, then the higher edge (`hotOrder`; "in play" is the live feed's word for the match, as on the rail), so that order follows the live body too. The home Fancy teaser and `/fancy` cards use the same live-first order (`hotOrder` on the teaser; `arrangeFixtures` on the cards). On phones the home page is the fixture-card rail (native snap scrolling, each card **80% of the screen** so the next match peeks) then a dedicated **High odds hits / Low odds misses** peek-card section, then **Props**: fixture hashtags and a short mixed player+fancy list (`mixHomeRows` in `src/lib/hot-lines.ts` — rank by `hotOrder` first, then rebalance only if a kind falls outside about one-third / two-thirds so a natural 4+2 is kept and a 6+0 is fixed; thin side trims the other instead of padding; today and tomorrow's player lines are both scored so a tomorrow chip is not fancy-only; one kind alone still fills the slot); from `lg` it is the rail plus the full lines table with match chips (`PropTable`, `MatchChip`). The phase switcher above the fixture rail (`HomePhaseBar`) switches **In play / Pre-match / Completed** (`?view=`, `src/lib/home-phase.ts`): the rail and the prop table show one bucket at a time so a live Test is not buried under finished rows. More on that bar opens the same pages as the sidebar More menu.

## Tournament stats (the Stats tab of `/league/<event idx>`)
`site/packages/engine/tournament.js` (tested in `site/tests/tournament.test.mjs` with hand-computed numbers), drawn by `components/app/tournament-stats.tsx`. No builder change: the lists are added up in the browser from the player files the player pages already read.
* **Editions.** The data has no season field, so an event's matches are grouped by gender and format (never mixed), then split where the calendar has a gap of more than 120 days, or 150 days inside one calendar year (IPL 2021, paused in May and resumed in September, is one season; IPL 2020 and 2021 are two). `?season=` carries the edition's key (the start year; a later edition in the same year gets `-<month>`; keys are given oldest first so a shared link keeps pointing at the same season). The season select and the bars of "Season by season" both change it. The newest edition opens.
* **Lists** (top 25, five shown): batting (most runs, highest scores, best average, best strike rate, most sixes, most fours, most 50+), bowling (most wickets, best figures, best average, best economy, best strike rate, most 4+ wicket hauls), overall (top performers = runs + 20 per wicket + 10 per catch + 25 per stumping, the player-performance scoring; highest team totals; lowest all-out totals). A list with no rows is left out. The three headline cards are most runs, most wickets and then the first of top performer, most sixes, best figures, highest score whose leader is a different player.
* **Rules.** Averages, strike rates and economy rates rank only players past a minimum of balls (`MIN_BALLS`: T20 60, ODI 120, Test 300, Hundred 60, T10 30, 60-over 120); with fewer than five that qualify (a three-match series) everyone is ranked and the list says so. A batter never dismissed has no average and is not ranked on it. Retired hurt is not an out. A scraped match has no dismissal detail, so a batter who has one has no average. Wickets exclude run outs, super overs are ignored, ties break on the next figure (more runs, fewer balls, fewer runs conceded) and then on the player index so the order never depends on which file arrived first. Fielding credits come from the fielding rows, so a fielder who neither batted nor bowled is left out of the points, as everywhere else on the site.
* **Leagues page and order.** `featuredEvents` (engine) orders the picker: big events (the `bigEvent` words of `config/home_rail.json`) that are live or due to start, those named in `PIN_FIRST` in `src/pages/Leagues.tsx` first (Big Bash: the women's season live, the men's due); then any other live league; then any other that is due; then those that finished lately, big ones first, larger first within each. **Live** is a match in the data within 10 days, or a fixture in the schedule file within three days (the match data lags the schedule: a season that has just started is not in it yet); **soon** is last season's start date a year on falling within 60 days ahead, or a fixture in the next 14 days (the schedule only reaches ten days out, so the calendar stands in for it). Schedule series names meet the data's event names through `seriesKey` (years, "league", "men's" and the short forms such as WBBL are ignored). A league linked with `?c=` that is not in the list is shown first. The page opens on the first one; `?season=` picks a season.
* **Cost.** A player lives in one of 64 files, so the lists read all of them (eight at a time, a progress bar says how many) the first time a season is opened; the result is cached for the visit. The facts strip and "Season by season" come from `matches.json` alone and need no player file. Season by season uses the same rule as the Markets tab (matches that count for summary markets, void games out) for scoring, except "Bat 1st won", which counts every match with a winner (a chase that ends early is a result), and shows editions of the same gender and format with at least three counted matches.

## Known limits (read the numbers as history)
* Provisional matches carry player totals (no batting order, dismissals or fall of wickets). They feed player props. Match Fancy uses a scraped match only when it **qualified** (`q = 1`: innings from ball-by-ball, or from the scorecard totals with 80% of overs). Totals-only rows stay out, so missing fours are never shown as 0. Highest over / most conceded / most wickets / extras / run-outs / the over tape (5/6/10/15 over runs, first over) need deliveries; a scrape without them is omitted from those markets. Live so-far for a session is the innings total only while `overs ≤ N` (or all out before N); once play is past N the live total is no longer the session score, so the overlay is blank rather than an inflated figure. The sample label says when scraped matches are included, and through which date.
* Fixtures only cover what the free schedule scrape and the odds sources list; men's domestic fixtures can be missing.
* Live scores lag up to about 20 seconds and come from the unofficial Source A pages. A player with no row yet is not "0 so far" (they may not have batted). "So far" is not a result until the match is final. Every priced player line on Hot props, the player page and the fixture table is the same `lineStanding` reading of that snapshot (server `lines` first, then the card). Fancy rows on Match Fancy, `/fancy` and the home snippet are the same snapshot via `fancyStanding` (innings totals, not player ids). A `bat_first` team run line (6/10/15/20 over session or the full innings) shows VOID once that side is bowling first; premium fours / sixes stay live for both. A so-far or a decimal price that moved since the last poll flashes green or red. **High odds hits** (over at 2.50 or longer that has cleared) and **Low odds misses** (over at 1.40 or shorter that has missed) are a dedicated home section between the fixture rail and the Props snippet (`engine/tape.js`); on a phone each tape card uses the same 80% peek rail as the fixture cards. Below the tape, Home shows **Props** with fixture hashtags (`MatchChip` pills in rail order) and a flat mixed player+fancy list for the chosen match (main fixture selected first; rows carry no match string). Empty lists use a shared `EmptyState` (icon, title, body) — Home Props, Player props, Fancy, Leagues, Saved sections, Match Fancy history, Trends and search. Player-performance so-far is the same scoring as the data: 1 per run, 20 per wicket, 10 per catch, 25 per stumping, with catches and stumpings taken from the scorecard how-out. A Test at stumps stays on the live feed (scores plus a Stumps / Lunch / Rain delay / Paused badge, not a Live pulse); it is not treated as finished until there is a result. The source's home list still shows that Test after the schedule page has dropped it; `/api/live` reads both, then our schedule file, and is never dropped just because twelve other finished matches also wanted a scorecard.
* Small samples are common: every answer shows `n` and a 90% interval for the hit rate. Fair odds have no margin and ignore form, pitch and XIs.

## Live lines in the tables (in-play)
There is no separate in-play section. While a match is on, its live lines are folded into the same data the tables read (`useLinesLive`, `engine/inplay-lines.js` `liveMerge`), so the existing rows show them with their own history figures and a red **Live** mark. The mark (`LiveBadge`) sits beside the row's name (the player, the market), never on the line. Where the line stood before the match is two words and a number on the quote / prices line ("was 31.5", `LiveOpened`, only when it has moved). Under the quote a thin bar (`LiveTrack`) shows what has been scored against the line, with a notch at the pre-match line; the so-far / to-go words follow it. A row carries nothing else of its own: no pill, no second line for the old prices.
* **Live lines are added beside the pre-match ones, never in place of them**: the pre-match line is the bet we track and settle, so its row stays (with its stats and so-far), and a live line is a row of its own with the red **Live** mark (`live: true` on the quote / fancy entry; the props list and Match Fancy keep a live row apart from the pre-match one). A batter's innings-runs line (any book that lists one) is a live line of his; in a Test it is his own side's current innings, not the match: the hook counts that side's innings in the live match (`innOf`), so it is his 1st / 2nd innings line (`inn`) and "was" comes from that innings' pre-match line, never the match total.
* Each live row carries where its line **opened** when it has moved: the pre-match line nearest evens (`openedOf` in `inplay-lines.js`, carried as `opened` on the quote / fancy entry and shown by `LiveOpened` and the notch of `LiveTrack`). **A line that opened in play** (a batter or side with no pre-match line in that scope) takes the first live line we saw as its `opened`: the snapshot job stamps it as `first` on the line (`stampFirst`) and keeps it in the row (`body.firsts`, carried from run to run, forgotten 20 minutes after the feed stops listing the line), so "was 24.5" and the notch show once the line moves and the bar turns green when he passes that first line, not only the line it has since moved to. A pre-match line, when there is one, still wins. A batter is linked to our player through the same book's own pre-match lines first (it spells him the same way, "M Taha"), then through the name resolver.
* **A live line is added once the pre-match line is passed.** While a batter's runs so far (`soFarOf` in `useLinesLive`, from the live board) are not past his main pre-match line in that scope (the one nearest evens, `openedOf`: a stray high line cannot hold it back), only the pre-match row shows. Once past it the live line is added (and its own stats, "Same spot"). The same for a milestone at a rung he was priced at (past the rung) and for a side's innings total (`teamRunsOf`: the side's runs in that innings). A batter, rung or side with no pre-match line in that scope (a debutant nobody priced, a 2nd innings, a rung that was not listed) shows the live line at once, and a live-priced row is never hidden for a thin history (`enoughHistory`): every supported live prop is shown. Other props (fours, sixes, wickets) do not come in the in-play feed as lines we read, so they stay pre-match with their live so-far.
* **The bar** (`LiveTrack`) is on every row that has a so-far (pre-match rows too): the runs so far against the row's line, green once past the line (or, on a live row, past the line it opened at), neutral before, red on a miss; a notch marks the pre-match line on a live row ("was 31.5" on the quote line says it in words, only when the line has moved).
* A side's innings-total line is a `team_total_runs` live row (its `inn`) of **Match Fancy**, beside the pre-match one (`fancyFor(..., live)`, `fancyOverview`; `marketRow` gives the row `live`, `OverviewRow` shows the mark).
* **A batter's milestone** ("to score 50", a half-century, a century; Yes / No, or the batters as outcomes: `milestoneRows`) is a line of his own in the **Props** (rung less a half: 49.5, 99.5; Yes is the over price, No the under price when listed), beside the pre-match line at that rung; a batter who cannot be linked to our player has no row. Milestones never go to Match Fancy.
* **Only what can be judged is shown.** Over / under runs over a stretch of overs (runs in the first N overs, overs 0-10, "6 over runs", powerplay: `keepLiveOu`) are live rows at the end of the Match Fancy list (`live-markets.tsx`). A single over or delivery, the fall of a wicket, wickets lost, method of dismissal, next batter out, odd / even and every other pick are **not shown** (the live feed has nothing to settle them by; they come back only with data that says whether they went over or under). The snapshot still holds them all; the filter is in `liveMerge`, so the site and the app agree. Match winner style markets are not shown either (not props or fancy). A batter the books list but we cannot link is still a live row of his own (`<name> innings runs`).
* Under a live innings-total row and a live batter row there is one line of history from the same spot (`live-spot.tsx`, engine `inplay.js` / `player-inplay.js`): how many past innings that were at the same score after the same balls went over and under the row's line ("Same spot: 6 over · 3 under"; the score, the band, the number of innings and the median finish are in its title). Counts of those innings, never a model; `small sample` under 8 innings (6 for a batter). The scope of a props row ("Runs · Complete match / 1st innings") is colour neutral; only the stat label carries the accent.
  * Team: past innings of the format and gender (every side, 3 years, same level) with the same runs after the same balls within 10% (at least 4 runs), bowled-out-before innings left out; a Test is included (innings number to 4; an innings the clock stopped is not a final total, `inningsComplete`); The Hundred is left out.
  * Batter, 10 to 150 balls in: his own past innings of that format in the same spot, from his progression (the runs after 10 / 20 / 30 / 50 / 75 / 100 / 150 balls faced in each innings, built into `pp/NN.json`, PROJECT_GUIDE 5.1, read on demand by `Store.playerProgression`); a straight line between marks.
  * The runs tape has no wickets, so wickets lost are not part of "the same spot".
Where the lines come from: `/api/inplay` (~15 s, asked only while a match is on) reads the Supabase row the in-play snapshot job keeps (docs/OPERATIONS.md "Cadence"): the price feed about every 15 s, and the other books that list started matches (Feed K, Feed E) once a minute, each line with its book's name. A live match is matched to our fixture by its two sides and the start: a side the books name without its level ("Bangladesh" for "Bangladesh U19", "India" for "India A") matches when the start is within 3 hours; and a live fixture no book priced before the start still gets its live lines (the site's fixture list stands in for the earlier lines). The other-books reader takes the matches live on the fixture list first (`inplay_extra.live_fixtures`) and reads up to 14 per book. A batter is linked to our player by the name resolver (`rz.players`, score 8 or more) on the two sides of the match; one that cannot be linked is a live row of his own.

**The site shows a filtered view; the log keeps all of it.** The tables above show what `liveMerge` folds in (and the live rows hide some markets). Every line the readers give, hidden ones included, is also appended to the Supabase table `inplay_log` by the same snapshot job, with the score at that moment, for later grading (PROJECT_GUIDE 5.10, docs/OPERATIONS.md "In-play line log"). The site never reads that table and settlement never uses it; nothing on a page depends on it.

## UI structure: reuse first
Prefer the patterns already on the site over inventing a new shell, chrome or interaction for each feature.

* **Reference beside the props, not above them.** On a match page the header is one card (the status, the scores and, while play is on, the live strip, with the scorecard one tap away) and stays short; anything else read as reference (form, grid, ground) is a chip that switches the page in place or a drill-in, never another stacked row between the score and the chips. The in-page Back shows from `lg` only; phones have the app bar's.
* **Drill-in pages, not one-off overlays.** A single market, player prop, or ground view is its own route (`/fixture/:id/fancy`, `/fixture/:id/ground`, `/player/:id`) with that page’s own header (title + back) — not a replay of the parent match chrome (no nested scorecard on ground). Do not add a bottom sheet, modal or bespoke drawer for that job unless it is clearly a filter/settings surface (Props Filters, Match Fancy Filters) or the user asks for it.
* **Reuse cards, chips, rails and headers.** Match lists use `FixtureCard`; filter rows use `Chip` / `PillGroup`; status badges use `sessionLabel` / `playState` the same way on home and on the fixture. Copy an existing page's layout before inventing a new composition.
* **Invent only when asked, necessary, or clearly better UX.** A new pattern needs a reason that the existing one cannot cover; document it here when it ships.

## Type and spacing scales (no hard-coded sizes)
Sizes are named by role and defined once, in `site/src/index.css` (`:root` plus `@theme`). Pages and shared components use the names, never `text-[13px]`, `text-sm`, `mt-5` or `gap-3`.
`site/src/lib/design-tokens.test.ts` fails the build if a governed file does; add a file to its `GOVERNED` list when its page is migrated (the old pages are not yet).

Web values (16 px rem). Native apps remap the names, not these numbers.

| --- | --- | --- |

| `text-title` | 18 px; lh 1.2; −2% tracking | section titles, sheet titles |
| `text-body` | 15 px; lh 1.25; −1% tracking | names, row titles, scores in cards |

Type is in rem, so it follows the browser's font-size setting. One `cn()` (`site/src/lib/utils.ts`) merges classes for the whole app, including shadcn's `ui/*` (they import it as `cn`; see the alias in `vite.config.ts` and `tsconfig.json`); it knows these scales, so `text-body` replaces a component's own `text-sm` instead of fighting it.

**Vertical rhythm.** A page is a `flex flex-col gap-section` of sections; a section is a `flex flex-col gap-stack` of blocks; related controls sit in a `gap-snug` group. Blocks never set their own vertical margins (the token test forbids `mt-*`/`mb-*`/`my-*` in governed files, except `mt-auto`), so every gap on a page comes from its parent.
**Switching tabs smoothly.** Content that changes height (a tab body, a filtered list) goes in `AnimatedHeight`, so the page eases between heights instead of snapping and the browser never clamps your scroll. The fixture page pins its tab bar under the pinned header (`sticky`) and, when you switch tabs while scrolled past the body, eases the new body to the top (then re-aligns once the height animation ends). Player page Lines / Game log / Splits chips scroll that section into view; chip rows scroll horizontally inside themselves and do not drag the page up to the chart.

## SEO and share cards

* **Per-page tags.** `site/src/lib/seo.js` `shareMetas` is the one list of tags (Open Graph + `twitter:card=summary_large_image` + `theme-color` + `og:image:alt`). The browser (`lib/title.ts`), the prebuilt pages (`scripts/seo.mjs`) and `/share` (`api/share.js`) all emit that list. Player, fixture and ground pages point `og:url` at `/share/...` and `og:image` at `/card/v7/...jpg` so a crawler stays on the card HTML instead of following through to the app shell. The version is in the path because X ignores `?v=` once it has cached a failed picture. Descriptions are clipped to ~180 characters so Facebook (~155 visible) and X (~200) do not cut mid-word.
* **Prebuilt pages.** `npm run build` ends with `site/scripts/seo.mjs`, which writes real HTML (title, description, canonical, share tags, JSON-LD, a short text body) for the static pages, every fixture and the biggest players, teams, competitions and grounds of the sitemap. The site address is `SITE_URL`, else the one in the sitemap the data build wrote. Every other path gets the app shell (no canonical; the app sets it).
* **Dynamic cards.** `api/og.js` draws a **1200×630** (1.91:1) **baseline JPEG under 300 KB** — the size Facebook, LinkedIn, WhatsApp, Discord, Slack, Telegram and iMessage all accept, small enough for WhatsApp's large preview, with `og:image:width/height` so Facebook can paint on the first share. X's 2:1 large card crops ~15 px; important type sits inside a ~64 px inset. A player-prop card is cricket-stats led: Satoshi name, hero OVER line + condensed price (book chip), crests, LAST 5 bars, L5/HIT pills, kit portrait on the right; Fancy.cash **F mark first** then the wordmark (`public/icon-192.png`). L5 form comes from `windowRate` on the shard `api/og.js` fetches over HTTP (2.5 s cap; shards not bundled — OPERATIONS). Host-relative photo paths resolve via `VITE_IMG_CDN`. A miss still returns a 1200×630 JPEG (never a PNG from a `.jpg` URL). Served `inline` with `Access-Control-Allow-Origin: *`. Photos fetch in parallel with a 1.5 s cap. `robots.txt` allows Twitterbot / Facebook / WhatsApp at `/` so they can read `/card` even if they also probe `/api`. Wrapped `photos.json` / `fixtures.json` are unwrapped with `DATA_WRAP_KEY` so the function can read them. `api/share.js` is a small page (Slack only reads the first 32 KB) with the JPEG in the body and no meta-refresh or JS redirect. Link-preview crawlers (X, Facebook/Instagram/Messenger, WhatsApp, Slack, Telegram, LinkedIn, Discord, Pinterest, Reddit, Teams, Bluesky Cardyb, Mastodon, LINE, Viber) hitting `/player`, `/fixture` or `/venue` are rewritten to that share HTML by `site/middleware.js`. Search indexers (Googlebot) still get the real page. The player page's Share button copies the `/share` link. A player URL with no stat/line still draws his booked prop when the books have one, so the picture is not an empty name card.
