# Cricket Props Hub: the free stats site (`site/`)

A free player-props and fancy-markets stats site built on this repo's data. Static pages plus two small serverless functions
(`/api/ask`, `/api/live`), hosted on **Vercel Hobby**. Nothing paid, no database, no model hosting.

## What it does
| Page | What you get |
|---|---|
| Home / **Ask** | Type a question in your own words (typos fine). A free Gemini model turns it into a *query plan*; the site runs that plan on the real data and shows the answer, the filters used, the sample size and the data freshness. |
| **Fixtures** | Upcoming internationals/leagues from `data/fixtures/upcoming.csv` only. The bookmaker feed is for odds, never for fixtures or start times (books serve different regions). Live scores (team totals, current batters/bowler, and player so-far vs booked lines) refresh about every 15 seconds from the Source A schedule, match and scorecard pages, **only for matches we have player-prop or fancy odds for**; they are never used to settle a prop. Props and Match Fancy tabs (and unpriced fancy markets) stay hidden when that match has no bookmaker line. |
| **Players** | Runs, balls, 4s, 6s, wickets, runs conceded. Hit rate over/under any line, a ladder of lines, median/mean, last-N form, fair decimal odds, split by opposition, venue, home/away/neutral, batting first/chasing, batting position, year and competition. One format at a time, never mixed. |
| **Teams & grounds** | Match totals and fancy markets: match 4s/6s, 30s, 50s, 100s, double-digit and single-digit scores, ducks, extras, run-outs, highest over, most runs conceded / most wickets by a bowler, top score, first over and first-N-overs session runs, team markets (a side's own innings), and who tops the batting card. Ground pages show match counts by format and the next fixture at that venue. Search (⌘K and the venues list) matches grounds as well as players and teams. |
| **Partnerships** | For any two batters: who is dismissed first, stand sizes, split by format, opposition and venue; opening pair only if you like. |
| **Prop Hunter** | The best-value props for upcoming matches from `value_bets/out/value_bets_latest.json`, read live from GitHub (falls back to the snapshot built into the site). |
| **Privacy / Terms / Docs** | Unlisted legal pages (`/privacy-policy`, `/terms-of-use`, `/docs`): what the site stores, that it is cricket stats and data, and that it does not offer, promote or encourage gambling. Not in the chrome, sitemap or search index; they load only if the URL is typed. `/privacy`, `/terms`, `/disclaimer` and `/responsible` redirect to those paths. |

See [SITE_MAP.md](SITE_MAP.md) for the page-by-page comparison with StatsHub.

## How the numbers are produced
```
Base all_json.zip ─┐
data/provisional/*.json ─┼─► python -m cricket_site.build ─► site/public/data/*.json ─► browser engine (site/packages/engine)
data/fixtures, value_bets ┘                                                              ▲
                                                question ─► /api/ask (Gemini) ─► plan ───┘  (validated, then run on the rows)
                                                Source A schedule + match + scorecard ─► /api/live (15 s cache) ─► fixture scores + live board + player so-far + fancy so-far + each priced player line settled (value, final, Cleared / Missed / Push, Not in XI)
```
* **Builder** (`src/cricket_site`, stdlib only): parses the ball-by-ball JSON into per-innings batting rows (position, innings order,
  runs/balls/4s/6s, dismissal), bowling spells, partnerships (who was out, runs, balls, opening flag) and match-market aggregates.
  Provisional (scraped) matches are added as player-total rows when Base does not have the fixture yet (same dedupe as
  `cricket-data query`: same teams, +/-1 day) and only when `link-players` gave the player a Base id.
  Output is ~35 MB of JSON (~12 MB compressed): `meta.json`, `index.json`, `matches.json`, 64 player shards `p/NN.json`, `fixtures.json`, `props.json`.
  I checked ~71,000 player rows against `data/players`: every difference was a super-over (the site ignores super overs on purpose).
* **Engine** (`site/packages/engine`, no dependencies, runs in the browser and in node): filters, hit rates, fair odds, markets, partnerships,
  name resolution with typo tolerance, the plan runner, and live-score parsing (`live.js`). **Every number on a page is computed here from the rows
  or from the live snapshot** — never from the LLM.
* **The model never supplies a number.** `/api/ask` (`site/api/ask.js`) sends only the question text to Gemini with a fixed instruction and gets
  back JSON, which `sanitizePlan` reduces to whitelisted fields. The plan is then resolved against the real player/team/venue tables and executed
  in the browser. If the key is missing, rate-limited or the reply is unusable, the built-in rule parser (`engine/nl.js`) answers instead.
* **Live scores.** `/api/live` (`site/api/live.js`) reads Source A's schedule, match and scorecard pages (no key; Source B is not used, its cards lagged its own header), caches ~15 seconds, and returns compact team
  scores plus batting/bowling so-far **only for matches in the book feed** (player props, event markets, or fancy). The fixture header shows a
  live board (current pair: avatars on the edges, name with runs/balls under it, partnership in the middle, last wicket, bowler, this-over deliveries with a divider at the over break, CRR/RRR)
  plus a Scorecard and Recent form accordion (both closed so props stay first). The closed Recent form row shows last 3 W/L chips per side so it fits on a phone; the open body is still last 5 in this format. Scorecard has batting (how-out, R, B, 4s, 6s, SR), extras, fall of wickets, yet to bat, and bowling (O, M, R, W, Econ) — the
  same columns Source A and Source B show. Games with no odds stay off
  the rail and off the live snapshot. The schedule page (cached ~5 min) lists the games and their URLs; scores, the current pair and rates come from the **match** page
  and the full card from **match-scorecard** (`getSC4`; `max-age` 10 s, robots-allowed; we do not call `$LIVE_SOURCE_BASE/api`), so a chase shows the chasing side's pair the moment it starts.
  The browser polls that route.
  **Playing XI.** The card lists a side's eleven (batters plus yet to bat) as soon as it is down to bat, so a prop row shows **Not in XI** and is dimmed when that side's eleven are all known and the player is not one of them. The other side stays unmarked until it has batted: the source only gives its XI through an app API we do not call. Pages are fetched from 90 minutes before the start so the batting side's XI is picked up at the toss. A priced match also stays in Hot props, with its last pre-match prices, for 24 hours after the start (6 days for a Test) and while the live feed still lists it as being played.
  Unofficial and can change. Every priced player line of a match is settled here (`lines` on each match: value, state, verdict, Not in XI), by the player's id through the identity table, so the browser does no matching of its own; while the match is on these are "so far", and a final number in a finished match is its result, stored in the archive (`docs/PROJECT_GUIDE.md` 5.4c). VOID/DNP rules still apply: a player with no row has no result. Fancy so-far is the same 15 s snapshot, read in the browser (`fancyStanding` in `live.js`: innings totals via `liveMarket`, then `lineVerdict`): Match Fancy, the Fancy cards and the home teaser overlay it at view time, so a 10-minute scored history does not freeze the live number. A so-far or a decimal price that moved flashes green or red, same words as a player prop (N so far / Cleared / Missed / Push). A fancy side run line tagged `bat_first` (6/10/15/20 over session, or the full innings) shows VOID once that side is bowling first; premium fours / sixes are not tagged and stay live for both.
  Kick-off, "today / tomorrow" and countdowns stay in the **viewer's time zone** (`site/src/lib/format.ts`).

## Cadence and what we show
A priced match stays on the site for **24 hours after kick-off (6 days for a Test / first-class)**, as one match, with the last **pre-match** prices plus live so-far. The UI never pretends we have moving in-play odds.

| Job | When | What it is |
|---|---|---|
| Odds / book lines | Hourly **09:00–23:00 IST** (`value-bets.yml` `30 3-17 * * *` UTC). Feed G's India runner ~20 minutes before that. | Closing pre-match player props and fancy only, for matches starting in the next **10 days** when a book has prices (`FEED*_HORIZON_HOURS`). Value-bet alerts use the next **7 days** (`WINDOW_HOURS`). Every adapter and `book_lines` drop `in_play`. After the first ball the next pull would empty the match; `carry_started` copies yesterday's closing prices for 40 h (T20/ODI) / 6 days (Test), and a Test's morning restamp of `start_utc` is merged onto the first morning so the file is not three SA vs AUS clones. |
| Live scores / so-far / Cleared | `/api/live`, ~15 s, Source A pages, **books-priced matches only** | The in-play layer we do have: team scores, player so-far, fancy so-far (`fancyStanding`), and every priced player line settled on the server. |
| Archive results | Same hourly value-bets job, `--results` against `/api/live` | Finished numbers stored on the match's archive file. |
| Fixtures scrape | Every 30 minutes (`scraper-update.yml` `7,37 * * * *`) | `upcoming.csv` for the rail and `/api/live` gap rows. |
| Site data deploy | Hourly at `:50` plus push to `site/` (`site.yml`) | Bundled `lines.json` can lag the GitHub `book_lines.json` the browser also fetches (1.5 s). |
| Ball-by-ball / Base | Daily 05:30 UTC | Not used for live props. |

Overnight Tests whose session sits outside 09:00–23:00 IST get **no new book pull** until the next morning. The site keeps the carried closing line and the 15 s scorecard.

**Test (and T20) line types.** Books do not price "3rd innings" / "4th innings" as match innings for a player. `inn` is the player's **own side's** 1st or 2nd innings. Unscoped (`inn` 0 / absent) is the whole Test (both innings summed). Show match totals and 1st / 2nd innings of *his side* when a book listed them pre-match; never in-play ladders around the current score, never 3rd/4th match innings. After the start: frozen line + so-far / Cleared / Missed / Push / Not in XI. Fancy **team** innings lines (`inn` 1 or 2 on a team total) are scored on that side's own 1st/2nd innings and shown as their own rows on Match Fancy and the Fancy cards (a live Test often has only those left after match totals come off). They are never mixed with the match total. Live tracking is the same 15 s poll as player props (`fancyStanding`): a side's own innings is `final` once that turn is over; a limited-overs team total is `final` with that innings; a Test match total and a whole-match market stay live until the match ends. A `bat_first` session or lambi voids once that side is bowling first (premium fours / sixes are not tagged).

The keep window (`keepMsFor` / `sameMatchWindow` in `site/packages/engine/lines.js`) is the only clock Hot props, the player page, `/api/live` matching and the rail's finished list share. The home list's extra "quiet day" filler (up to 4 days of finished limited-overs matches when fewer than three games are lined up) is display-only so the rail is not bare.

## Settlement rules and definitions
* T20 summary markets are void unless both innings reach 80% of the scheduled balls (96 of 120); ODI likewise (240 of 300); The Hundred 80 of 100; T10 48 of 60; 60-over 288 of 360.
  Tests: void unless there is a result, or 300 overs (5-day) / 200 overs (4-day) were bowled. Void matches are left out of match/team markets.
* 30s = 30-49, 50s = 50-99, 100s = 100+, double-digit = 10+, single-digit = 1-9 (ducks excluded). Team markets count only the team batting first.
* Retired hurt is not a wicket. Penalty runs count. Runs conceded = batter runs + wides + no-balls + penalty (as in `data/players`). Super overs are ignored.
* Formats: T20 = T20 + T20I, ODI = ODI + 50-over List A, Test = Tests only, **The Hundred / T10 / 60-over are their own formats**. A T20 in a Test series must not price the Test. First-class (`MDM`) is not included.
* Fair decimal odds = 1 / hit rate on the filtered sample (pushes on whole-number lines are void). Decimal odds only.
* Home/away/neutral is *inferred*, because Base has no home flag: the event ("X tour of Y"), the venue's tour history, its country in
  `value_bets/mappings/venue_geo.csv`, then the team that plays at least half of the venue's internationals. Unknown hosts are left out of home/away filters.

## Player screen (app-style UI)
The player page (`/player/<idx>`) is `site/src/pages/Player.tsx`: a sticky app bar on phones, a prop rail of only the stats a book prices for this player on the nearest match (`bookStatsFor`; the chips are hidden when none are listed), a hero (photo, name, round buttons), a format switch, one tappable bar chart with Over/Under, a line stepper and look-back pills that show each window's hit rate (`engine/windows.js`, unit-tested by hand-computed numbers), a bottom sheet for filters and for a tapped game, and Lines / Game log / Splits tabs. **Desktop (`lg+`)** is a 12-column board, not a stretched phone column: a compact metrics strip, then the chart first (8) beside the booked lines (4), then the this-match card (5) under the chart. Look-back pills sit under the bars. Ground vs opponent hit rates sit as two cards inside the match block. On a phone it is still one column (metrics, chart, this-match, lines). The **next match** card (`components/app/next-match.tsx`) is the nearest booked match still in the keep window (24 hours after the start, 6 days for a Test — the same window Hot props uses), including one that is in play or just finished: both sides and the ground; the books' decimal over/under on the line the chart is on; and, once the match has started, where that line stands (`lineStanding`: so far / N to go / final / Cleared / Missed / Push, the same words as Hot props). A so-far or a book's price that just moved flashes green or red with an arrow (`Tick`, from the 15 s live poll — there is no websocket). How often he has cleared that line at that ground and against that opponent (the same chart entries, this format; DNP/VOID out) sits under the prices, each with a fair decimal price (`engine/next-match.js`). The heading is "This match" while it is live or finished. A finished listed match is not replaced by the schedule's next unpriced game, so the page does not say "No props live yet" while Hot props still has her. With no booked line it says "No props live yet" rather than inventing one from the median. Prop-category chips (`bookStatsFor`) use that same keep window, and two books that stamp the same fixture minutes apart are one match (a sixes line is not dropped because another feed listed player performance 30 minutes earlier). An explicit `?stat=` in the link is kept. The chart keeps the line and side in the URL with `replaceState`, so a page can be shared. UI library: shadcn/ui (Radix) with Motion for animation; see PROJECT_GUIDE 5.3.

**Bookmaker lines.** The value-bets pipeline saves every matched two-sided player line (runs, sixes, fours, wickets; decimal over/under per book) to `value_bets/out/book_lines.json` (`src/value_bets/booklines.py`, matched to Base player ids). The site builder bundles it as `data/lines.json`, and the player page reads the live file from GitHub (falling back to the bundle). For a player with a priced upcoming match, the chart opens on the market's **main line** (the one priced closest to evens, `engine/lines.js`) instead of the median-based default, and a "Bookmaker lines" card shows each book's prices, the no-margin market probability and his own hit rate over each line; tap a line to put it on the chart. Players or stats with no market line still chart form on a median line (floor(median) + 0.5, `suggestLines`) so you can look at history, but the next-match card does not treat that as a listed prop. Books rarely quote the same line for a player and stat, so a Hot props / fixture Props row lists each book's own line and over price under the row (`bookQuotes` in `engine/lines.js`; `BookQuotes` in `hot-props.tsx`). A **single book still shows its mark and price on the third row of the prop card**, same place as when several books quote; the "+N books" toggle appears only when another book is quoting. With 2+ books the lowest line, and the best price at it, is in the accent colour. The row's edge, hit rates and bars stay on the main line. The ground chip uses a short stadium name (`shortVenue` in `lib/format.ts`: WACA, MCG, Wankhede), with the full venue on the title. On the phone prop card the bookmaker mark is row 3; **N in L10** and **hits/played at the ground** sit on row 4 with the form bars (EDGE stays top-right). Fancy rows (`OverviewRow`) do the same: the book's mark sits next to the price even when it is the only book; `BookTable` is only the extras. Every place a book's price appears (those rows, the player page's lines, the fancy cards) marks the book with `BookBadge` (`components/app/book-badge.tsx`): the brand's logo from `site/public/books/` when `lib/books.ts` lists one (the mark as the site owner supplied it, cropped or scaled and never redrawn; the site is dark, so a white or reversed version is best), else a plain name chip; a logo that fails to load falls back to the name. The About page and the terms page say the names and logos are their owners' trademarks, shown only to say where a price comes from.

**Edge.** The EDGE figure on Hot props, the player page's best-price line and Match Fancy is `shrunk chance x best price - 1` (`sideEdge` in `site/packages/engine/stats.js`, unit-tested by hand-computed numbers). The hit rate is the window shown (L5 / L10 / L20 / L30 / All; the season and head-to-head windows on Hot props), over the games he played. It is pulled toward the market's no-vig chance of that side, `(hits + 10 x market) / (played + 10)`, so the market counts as ten extra games: 8 of 10 against an even market is 0.65, not 0.80, and 40 of 60 is 0.643, not 0.667. The price is the best any book offers for the side, and no edge is shown under ten played games. At 1.90 / 1.90 a record that matches the market gives -5%, the books' margin. It is a measure of expected profit per unit, not a stake size or a promise: nothing here models the matchup, ground or conditions except through the market's price (the hourly pipeline's context model is not used by the site yet).

**Innings scope (Tests).** For a Test batter the books price the match total and his side's first innings (`inn` on the line, `docs/VALUE_BETS.md`), and the page has a three-way **Both innings / 1st innings / 2nd innings** switch (`?scope=0|1|2`, shown for every Test batting stat, a scope with no priced line still charts that innings; the sheet's "batted first / chasing" filter is a separate thing). The switch picks the lines (`bookLinesFor(..., inn)` gives one scope at a time, `bookScopesFor` lists what is priced) and the chart: a first-innings line is charted against what he made in his side's first innings of each Test only (`filters.tinn`, from `store.teamInningNo`: his side's own n-th turn, not the match's n-th innings; the plan field is `team_innings`), never against match totals. With no `scope` in the link the page opens on the match total when it is priced, else on the first scope that is. The Hot props list gives a first-innings line a row of its own, tagged with its scope.

**Props are never deleted.** A fixture that has arrived and been priced keeps its props: the list on the home page lets a finished match go after a day (`shownFixtures`), but the fixture's own page (`/fixture/<id>`) always works. When the schedule no longer lists the match, or the live book file has let its lines go, the page reads the match's archive file (`value_bets/archive/YYYY-MM/<fixture id>.json`, see `docs/VALUE_BETS.md`) through `useFixtureBooks` (`src/hooks/useEngine.ts`, `loadArchive` in `src/lib/feeds.ts`; the id is checked against the fixture-id pattern before it becomes a URL). `archiveFixture` rebuilds the fixture from the file and `withArchive` adds its lines to the book doc (`site/packages/engine/lines.js`, unit-tested); the props list scores them from the player's history like any others, and shows each result from the file's `results` (stored by the server once the match was over, `docs/VALUE_BETS.md`), else from the data once the match is in it.

**Home rail order, and settings that need no deploy.** The rail (`src/lib/priority.ts`) clusters by series (`arrangeFixtures`): matches in play lead, then those starting within 24 hours (still to come, then finished, newest first), then later games of that series up to 10 days. Series with a match in play lead; among the rest a kick-off in the next 24 hours leads a bigger match later in the week, with a lift for the viewer's own team (read from the time zone, then the language), their part of the world and the big tournaments. A just-finished T20 stays next to that series' next game instead of falling behind every other upcoming card. Finished limited-overs matches stay 24 hours from the start (`shownFixtures` / `keepFinished`; a Test keeps 6 days). On a quiet day, finished limited-overs matches can stay up to 4 days so the rail is not bare. The knobs are published as `config/home_rail.json` and read at view time (`loadRail` in `src/lib/feeds.ts`, `useRail`), so changing one is a commit to that file on `main`, live in about 5 minutes (the raw-file cache), with no site build: `tiers` (group order), `bonus` (`home`, `homeWomen`, `region`, `event`), `bigEvent` (whole words looked for in the series name), `standing` (a team key such as `southafrica` to a number) and `region` (a team key to its part of the world). Anything missing or mistyped keeps the built-in value (`sanitizeRail` reads only these keys, with limits), and a test keeps the file equal to the built-in settings, so edit both when a built-in default is meant to change.

**How the home page loads (what shows when).** The three feeds the rail reads (the book lines, `config/home_rail.json`, `/api/live`) are started in `main.tsx` before the data files finish (`prefetchFeeds`, `src/lib/queries.ts`), not when the page mounts. `/fancy`, `/props` and a fixture page prefetch `/api/live` the same way (the rail file stays home-only). `loadLines` fetches the bundled `lines.json` and the live file together and keeps the newer by `generated_at_utc`; the live file is given up on after 1.5 s. The rail (`useHomeRail`) shows a skeleton until the schedule and the lines are in, so it is never the unpriced schedule that the priced list then replaces. Matches in play lead the rail, so the live state has to be there for the first paint: the last `/api/live` body is kept on the device for 30 minutes (`src/lib/live-cache.ts`) and is the live query's starting point (stale, so the fresh body is asked for at once), which puts live matches in front on the first paint of a revisit. With no kept body the rail waits up to 1.2 s for the live scores (0.8 s for the rail file) and then paints with what it has. A fresh body that changes a match's state (gone live, ended) re-sorts the rail; one that changes nothing leaves it as it was. **Hot props** score the selected day's lines (`hotLines`, `src/lib/hot-lines.ts`; tomorrow is its own query, run when asked for; a fixture page scores only its own match). A match that has already started and is still in the keep window — 24 hours, 6 days for a Test, because the books restamp a Test each morning — is today's, so day 4 of a Test is not dropped because its first start was earlier in the week. The player files come eight at a time with the busiest file first, and the rows show once a page of them is scored, then as more files land. Rows of a match in play come first, then the higher hit rate, then the higher edge (`hotOrder`; "in play" is the live feed's word for the match, as on the rail), so that order follows the live body too. The home Fancy teaser and `/fancy` cards use the same live-first order (`hotOrder` on the teaser; `arrangeFixtures` on the cards). On phones the home page is the fixture-card rail (native snap scrolling, each card **80% of the screen** so the next match peeks) then a dedicated **High odds hits / Low odds misses** peek-card section, then a short Hot props teaser; from `lg` it is the rail plus the full lines table with match chips (`PropTable`, `MatchChip`). A floating glass bar at the bottom (`HomePhaseBar`) switches **In play / Pre-match / Resulted** (`?view=`, `src/lib/home-phase.ts`): the rail and the prop table show one bucket at a time so a live Test is not buried under finished rows. More on that bar opens the same pages as the sidebar More menu.

## Known limits (read the numbers as history)
* Provisional matches carry player totals (no batting order, dismissals or fall of wickets). They feed player props. Match Fancy uses a scraped match only when it **qualified** (`q = 1`: innings from ball-by-ball, or from the scorecard totals with 80% of overs). Totals-only rows stay out, so missing fours are never shown as 0. Highest over / most conceded / most wickets / extras / run-outs / the over tape (5/6/10/15 over runs, first over) need deliveries; a scrape without them is omitted from those markets. Live so-far for a session is the innings total only while `overs ≤ N` (or all out before N); once play is past N the live total is no longer the session score, so the overlay is blank rather than an inflated figure. The sample label says when scraped matches are included, and through which date.
* Fixtures only cover what the free schedule scrape and the odds sources list; men's domestic fixtures can be missing.
* Live scores lag up to about 20 seconds and come from the unofficial Source A pages. A player with no row yet is not "0 so far" (they may not have batted). "So far" is not a result until the match is final. Every priced player line on Hot props, the player page and the fixture table is the same `lineStanding` reading of that snapshot (server `lines` first, then the card). Fancy rows on Match Fancy, `/fancy` and the home teaser are the same snapshot via `fancyStanding` (innings totals, not player ids). A `bat_first` team run line (6/10/15/20 over session or the full innings) shows VOID once that side is bowling first; premium fours / sixes stay live for both. A so-far or a decimal price that moved since the last poll flashes green or red. **High odds hits** (over at 2.50 or longer that has cleared) and **Low odds misses** (over at 1.40 or shorter that has missed) are a dedicated home section between the fixture rail and Hot props (`engine/tape.js`); on a phone each tape card uses the same 80% peek rail as the fixture cards. Player-performance so-far is the same scoring as the data: 1 per run, 20 per wicket, 10 per catch, 25 per stumping, with catches and stumpings taken from the scorecard how-out. A Test at stumps stays on the live feed (scores plus a Stumps / Lunch / Rain delay / Paused badge, not a Live pulse); it is not treated as finished until there is a result. The source's home list still shows that Test after the schedule page has dropped it; `/api/live` reads both, then our schedule file, and is never dropped just because twelve other finished matches also wanted a scorecard.
* Small samples are common: every answer shows `n` and a 90% interval for the hit rate. Fair odds have no margin and ignore form, pitch and XIs.

## Run it locally
```bash
cd site && npm ci && npm test          # engine + resolver + parser + API handler + components (node >= 20)
npm run dev                            # http://localhost:4173  (set GEMINI_API_KEY to try the AI parse)
```
Put `SITE_URL` (the public site, same GitHub variable) in gitignored `site/.env.local`. The dev server then proxies `/data`, `/api/gate` and `/api/live` so the UI uses production JSON and scores. Unset it to serve a local `python -m cricket_site.build --out site/public/data` instead (needs the Base zip; ~30 s).
Python tests: `pytest -q tests/site`. The JS tests run on a tiny synthetic dataset with hand-known numbers
(`tests/site/synth.py`, regenerated by `python scripts/make_site_fixture.py`; a pytest fails if the committed fixture is stale).

## Deploy (Vercel Hobby, free)
The Vercel project root is `site/` (static `public/` + `api/ask.js` + `api/live.js`; `site/vercel.json` already sets this).
1. **Once:** `cd site && npx vercel link --project cricket-props-hub` then, after building the data, `npx vercel deploy --prod`.
2. **AI key for the chat box.** Either **xAI Grok**: create a key at console.x.ai (API Keys), add it as the Vercel env var `XAI_API_KEY`, and set `XAI_MODEL` to a model name from the console's Models page (Grok API usage is billed per token, a few hundred tokens per question; check your credits). Or **Gemini (free tier):** create a key in Google AI Studio, then add it as the *Vercel* environment variable `GEMINI_API_KEY`
   (Project → Settings → Environment Variables, Production) and redeploy. Optional: `GEMINI_MODELS` (comma list, default

The builder, the review list of priced players it could not link, and the hand-checked file `data/mappings/player_identity.csv` are described in `PROJECT_GUIDE.md` 5.7. ## Player photos and team logos
Sources, in order: **Source A** (the repo already scrapes it) then **Wikidata/Wikimedia Commons**, then a flag (national sides) or initials/silhouette.
The builder reads Source A's public sitemaps (`$LIVE_SOURCE_BASE/crex_sitemap/player.xml`, `team.xml`: ~9.8k players, ~1k teams), matches Source A full names to Base
names conservatively (surname + first initial, ambiguous names skipped, see `src/cricket_site/crex_assets.py`) and stores only ids in `data/photos.json`.
The browser loads images from Source A's CDN (`$IMG_CDN_BASE/players/org/<id>.png`, `/Teams/<id>.png`); nothing is copied into the repo.
About 54% of recently active players and most national and franchise teams get a Source A image today; the rest fall back. Those images belong to Source A:
check their terms before using the site commercially, or replace the source later by returning a different URL from `playerPhoto` in `site/src/lib/photos.js`.

## Our own copy of the images and id maps (Supabase, free plan)
So the site keeps working if Source A changes or removes its images, `src/cricket_site/assets_sync.py` copies each player photo / team logo once into a
public Supabase Storage bucket (`avatars`) and records it in Postgres (`assets`, `crex_players`, `crex_teams`; public read, writes only with the service key).
The Site workflow runs it hourly (resumable, at most `SYNC_LIMIT` new images per run, politely paced) and adds `base` + `s` (ids we hold) to `photos.json`;
the browser then tries our copy first and Source A second. Setup: repository variable `SUPABASE_URL` and secret `SUPABASE_SERVICE_KEY`
(dashboard -> Project Settings -> API Keys -> service role / secret key; never commit it). Without them the step is skipped and Source A is used directly.
Schema: see the `cricket_assets_schema` migration (tables above plus the `avatars` bucket: public, 200 KB limit, png/webp/jpeg only).

## UI libraries and the iOS / Android apps
The apps are planned natively (Expo / React Native), like props.cash, whose website is a plain React SPA with separate store apps. So the website and the apps share
**data, logic and token names, not components**:
* `site/packages/engine/*` (plain ESM, no DOM) and the JSON data files are the shared core. Keep every number and rule there; never import React or the DOM into the engine.
* Web UI uses free MIT components from the shadcn CLI and its registries (`@magicui`, `@kibo-ui`, `@originui`, `@animate-ui` are registered in `site/components.json`; add with `npx shadcn@latest add @kibo-ui/<name>`),
  not hand-built widgets. Check the install diff: the CLI can overwrite `ui/*` files and the colour tokens in `index.css`. Paid libraries are not used.
* Charts stay SVG (no extra chart package). A **heatmap** is used only where the data is two-dimensional or a hit-rate scan: the team/fixture player grid (colour by how far a cell sits from the line) and a split heat strip when a split has five or more groups. A **donut** is used only when a form window has three or more outcome kinds (cleared / missed / push / not counted); two-way over/under stays a gauge or bars. Form over games stays a bar chart. Paid kits (Cue Design and similar) are not used. An area chart is not used: form is discrete games.
* Prefer touch-first components: nothing that only works on hover (for example the Magic UI dock's magnification), `h-control` / `size-control` for tappable chrome, and `env(safe-area-inset-*)`
  for fixed bars (`viewport-fit=cover` is set in `site/index.html`, which iOS needs for the insets to be non-zero).
* The **look** is iOS-inspired (true-black, system grays, blur, fully rounded pills, a segmented control, the classic iOS tab bar on phones and tablets (Ionic's `ion-tab-bar` web component, MIT, forced to iOS mode, translucent with the hairline on top), a source-list sidebar from `lg` with Play / More groups). Filter and match chips are shadcn `ToggleGroup` via `PillGroup` (filled selected pill, Motion slide); overlapping crests use `AvatarGroup`; live/session on a chip is a `Badge`. The **sizes** are a compact web scale so the same site reads well in a desktop browser and in Android/iOS browsers. Do not fork the website by user-agent; one set of values, every device. Dark only. There is no account or Guest profile menu: Saved is a header icon. Legal pages (`/privacy-policy`, `/terms-of-use`, `/docs`) are unlisted: not in the chrome or sitemap. The site positions itself as cricket stats and data; it does not offer, promote or encourage gambling.

When the Expo apps exist, reuse the same role names (`text-body`, `gap-stack`, `control`, `chip-radius`, …) from `site/src/index.css` `:root`. Swap only the values: HIG on iOS (17 px body, 44 px controls), Material 3 on Android. Do not copy web pixel values into native, and do not copy native HIG sizes back onto the website.

## Type and spacing scales (no hard-coded sizes)
Sizes are named by role and defined once, in `site/src/index.css` (`:root` plus `@theme`). Pages and shared components use the names, never `text-[13px]`, `text-sm`, `mt-5` or `gap-3`.
`site/src/lib/design-tokens.test.ts` fails the build if a governed file does; add a file to its `GOVERNED` list when its page is migrated (the old pages are not yet).

Web values (16 px rem). Native apps remap the names, not these numbers.

| Type | Web | Used for |
| --- | --- | --- |
| `text-display` | 24–28 px, fluid | page title |
| `text-title` | 18 px | section titles, sheet titles, key values |
| `text-body` | 15 px | names, row titles, primary text |
| `text-callout` | 13 px | secondary lines, chips and control labels |
| `text-footnote` | 12 px | meta and captions |
| `text-caption` | 10 px | micro labels (EDGE), small badges, tab labels |
| `text-metric` / `text-stat` | 20 / 30 px | timers and big numbers / hero statistic |

| Spacing | Web | Used for |
| --- | --- | --- |
| `hair` | 4 px | icon and text micro gaps |
| `tight` | 6 px | inside a component, chip rows |
| `snug` | 10 px | between controls in a row, list-row padding |
| `stack` | 16 px | between stacked blocks |
| `group` | 20 px | between groups inside a section |
| `section` | 32 px | between page sections |
| `inset` | 14 px | padding inside cards and panels |
| `gutter` | 14 px, 20 px from md, 24 px from lg | page side padding; list rows use it so photos line up with the page edge |
| `control` | 36 px | chip, icon-button and tab height (`h-control`, `size-control`) |
| `header` / `tabbar` / `row` | 48 / 49 / 56 px | top bar, phone tab bar, list-row min height |
| `fixture-card` | 80vw on phones, 20 rem from lg, 22 rem from 1440 | home rail and high-odds / low-odds peek cards |

Type is in rem, so it follows the browser's font-size setting. One `cn()` (`site/src/lib/utils.ts`) merges classes for the whole app, including shadcn's `ui/*` (they import it as `cn`; see the alias in `vite.config.ts` and `tsconfig.json`); it knows these scales, so `text-body` replaces a component's own `text-sm` instead of fighting it.

**Vertical rhythm.** A page is a `flex flex-col gap-section` of sections; a section is a `flex flex-col gap-stack` of blocks; related controls sit in a `gap-snug` group. Blocks never set their own vertical margins (the token test forbids `mt-*`/`mb-*`/`my-*` in governed files, except `mt-auto`), so every gap on a page comes from its parent.
**Switching tabs smoothly.** Content that changes height (a tab body, a filtered list) goes in `AnimatedHeight`, so the page eases between heights instead of snapping and the browser never clamps your scroll. The fixture page pins its tab bar under the pinned header (`sticky`) and, when you switch tabs while scrolled past the body, eases the new body to the top (then re-aligns once the height animation ends). Player page Lines / Game log / Splits chips scroll that section into view; chip rows scroll horizontally inside themselves and do not drag the page up to the chart.

## SEO and share cards

* **Per-page tags.** `site/src/lib/seo.js` `shareMetas` is the one list of tags (Open Graph + `twitter:card=summary_large_image` + `theme-color` + `og:image:alt`). The browser (`lib/title.ts`), the prebuilt pages (`scripts/seo.mjs`) and `/share` (`api/share.js`) all emit that list. Player, fixture and ground pages point `og:url` at `/share/...` and `og:image` at `/card/v7/...jpg` so a crawler stays on the card HTML instead of following through to the app shell. The version is in the path because X ignores `?v=` once it has cached a failed picture. Descriptions are clipped to ~180 characters so Facebook (~155 visible) and X (~200) do not cut mid-word.
* **Prebuilt pages.** `npm run build` ends with `site/scripts/seo.mjs`, which writes real HTML (title, description, canonical, share tags, JSON-LD, a short text body) for the static pages, every fixture and the biggest players, teams, competitions and grounds of the sitemap. The site address is `SITE_URL`, else the one in the sitemap the data build wrote. Every other path gets the app shell (no canonical; the app sets it).
* **Dynamic cards.** `api/og.js` draws a **1200×630** (1.91:1) **baseline JPEG under 300 KB** — the size Facebook, LinkedIn, WhatsApp, Discord, Slack, Telegram and iMessage all accept, small enough for WhatsApp's large preview, with `og:image:width/height` so Facebook can paint on the first share. X's 2:1 large card crops ~15 px; important type sits inside a ~64 px inset. A player-prop card is the share picture: name and team on the left, portrait on the right, team crests in a white circle (full mark, sat at the tip so a badge is not cropped), the Fancy.cash mark (`public/icon-192.png`) and wordmark at the top-right tip, the book's own logo from `public/books` on the listed-price chip, L5 mean and hit rate from `windowRate` on the last five played innings in that format (DNP / VOID never count; `api/og.js` reads the player shard, 2.5 s cap), the booked line / prop / listed price, opponent (no kickoff time) and five bars of those innings vs the line. A miss still returns a 1200×630 JPEG (never a PNG from a `.jpg` URL: X drops a type mismatch, never a 302 a crawler would follow). The image is served `inline`, with `Access-Control-Allow-Origin: *`. Photos are fetched in parallel with an 800 ms cap so X's crawler is not left waiting. `robots.txt` allows Twitterbot / Facebook / WhatsApp at `/` so they can read `/card` even if they also probe `/api`. Wrapped `photos.json` / `fixtures.json` are unwrapped with `DATA_WRAP_KEY` so the function can read them. `api/share.js` is a small page (Slack only reads the first 32 KB) with the JPEG in the body and no meta-refresh or JS redirect. Link-preview crawlers (X, Facebook/Instagram/Messenger, WhatsApp, Slack, Telegram, LinkedIn, Discord, Pinterest, Reddit, Teams, Bluesky Cardyb, Mastodon, LINE, Viber) hitting `/player`, `/fixture` or `/venue` are rewritten to that share HTML by `site/middleware.js`. Search indexers (Googlebot) still get the real page. The player page's Share button copies the `/share` link. A player URL with no stat/line still draws his booked prop when the books have one, so the picture is not an empty name card.

## Mobile-first shell, Props screener and saved items (2026-10-31)
* **Packages** (npm workspaces inside `site/`, so the Vercel deploy that uploads `site/` still has them): `site/packages/tokens` (`tokens.json` is the one source for colours, sizes, type scale, spacing, chart colours, elevation and breakpoints; `npm run tokens` writes `src/tokens.generated.css`, `npm run build` runs it first, and a test fails when the committed CSS is stale or a token points at itself) and `site/packages/storage` (key-value adapter: web `localStorage` now, MMKV on native later; plus pure helpers for saved props, filter combinations and recents). The engine is `site/packages/engine` (`@cricket/engine`, imported as `@cricket/engine/<file>.js` by the app, the tests, `api/*.js` and `scripts/seo.mjs`; `photos.js` moved with it because `card.js` needs it). It stays plain ESM with no DOM, so a native app can import it unchanged.
* **Navigation:** phone bottom bar is Fixtures, Props, Fancy, Saved (`layout/nav.ts`); a page one level down (player, team, match) gets a back button in the phone header (`isTopLevel`); from `lg` the left sidebar. The Props page has a floating filter button on phones.
* **Props screener filters live in the URL** (`lib/screener.ts`, tested): `stat`, `win`, `day`, `match`, `team`, `fmt`, `comp`, `min` (minimum hit rate), `value`, `inns`, `sort`, `bars`. Only what differs from the default is written, unknown values fall back to the default, and `/props` canonicalises to itself (the canonical link never carries the query). Going to another tab and back to `/props` restores the session's last view. The filter view (`components/app/screener-filters.tsx`) is full screen on phones and a right drawer from `lg`: grouped accordions that show their value, edits held until Apply, Clear all, Save and share. It offers only values the rows really have (format, team, competition come from the day's rows). Rows with too few games in the chosen window are left out of a minimum-hit-rate filter, never guessed. `inns` (Batting innings: any / batted first / chasing) scores every row again from only the games where his side batted first or chased (the engine's `innings` filter), so it is its own cached query and its samples are smaller; matches without innings detail (provisional) drop out. There is **no pace-versus-spin filter**: nothing in the data says what type a bowler is (the base data and the ball-by-ball files carry the bowler, not the style), and a guess from names would be invented. To add one, first add a reviewed player-level bowling-style table (like `data/mappings/player_identity.csv`), then expose it as an engine filter and a section in `screener-filters.tsx`.
* **Saved** (`lib/saved.ts`, `pages/Saved.tsx`): watchlist props (key `prop:<player>:<stat>:<line>:<format>`), players and teams, saved filter combinations (name + query string, the same string is the share link) and recently viewed players, all on this device. No accounts, nothing is sent anywhere.
* **Player page:** summary is three metrics on a phone (six from `lg`) so the chart is on the first screen; chart is 240 px tall on phones; the alternate-lines list opens as a bottom sheet on phones (inline panel from `lg`); under the chart the sample size is stated and fewer than 5 games gets a warning with Clear filters; an empty sample says which filters caused it.
* **SEO:** `/props` and `/fancy` are in `ROUTES` (`src/lib/seo.js`), so `scripts/seo.mjs` prerenders them with title, description and canonical, and the Python builder lists them in `sitemap.xml`. Filtered views are the same canonical page. `/saved` stays `noindex`.

* **Fonts:** Props.Cash's computed fonts are Diatype (400/500/700) for text and Diatype Condensed 500 for numbers; both are paid, so the app uses Inter (text) and Barlow Semi Condensed (numbers and `label-cap` labels, at text size 15-20 px) with Bebas Neue for brand only. The rule is written at the top of `site/src/index.css`; the stack lives in `packages/tokens/tokens.json`.
