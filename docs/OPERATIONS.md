**Source hosts live in the environment, never in the tree.** No tracked file names a data source's host (`scripts/check_public_safe.py` fails on it, comparing hashes so the script lists none), and committed data stores host-relative links. Locally put the same names in a git-ignored `site/.env.local` (the dev server loads it into the API handlers) or export them before running Python. Tests use placeholder hosts (`tests/conftest.py`, `site/tests/*`).

Never commit `.env*`, tokens, or keys. `site/.env.local` created by `vercel link` must be deleted (it holds an OIDC token).

**Anti-scrape (silent, browsers are not prompted):** set `DATA_WRAP_KEY`. The Site workflow wraps the smaller `/data` JSON files (not `index.json` / `matches.json` / shards: those are too big to decrypt on a phone) and `/api/live` wraps the same way, so a Network-tab response is `{v, iv, ct}` rather than scores. `/api/gate` puts the key in the `X-Cd-K` header, not the JSON body. The Edge middleware requires the `/api/gate` cookie (known scraper UAs are refused; `meta.json` stays readable). A 403 on `/data` is `no-store` so a first-request cookie race is not cached as "Data not found". The hourly archive job unwraps `/api/live` with the same secret. This is a speed bump, not a secret from a real browser: the page still has to unwrap to draw numbers.

## Player profiles
Role / batting hand / bowling style are collected by the Site workflow's "Player profiles" step into `data/profiles/profiles.csv` (PROJECT_GUIDE 5.9). It needs no new secret. To backfill faster run the Site workflow by hand with the `PROFILES_LIMIT` variable raised for a while (about 2 s per page; the step stops after 600 s). Locally: export `LIVE_SOURCE_BASE` and `LIVE_SITEMAP_DIR`, run a site build, then `python -m cricket_site.profiles`. A step that fetched nothing is not a failure (source down, or every linked player already stored); the job log prints `fetched/found/empty/failed/pending`.

## Cadence (odds vs scores)
Job times, what is shown, and Test innings 0/1/2 rules: [SITE.md — Cadence and what we show](SITE.md#cadence-and-what-we-show). Short version: odds are hourly, round the clock, **pre-match only** (no in-play prices); `/api/live` is ~15 s scores and so-far for books-priced matches; a priced match stays 24 hours after kick-off (6 days for a Test) as one match with the closing line plus live so-far. ## Routine tasks
**Rotate the xAI key**: console.x.ai -> API Keys -> create new, delete old; then `cd site && printf '%s' "$NEW" | npx vercel env add XAI_API_KEY production --sensitive --yes` (or the dashboard), then redeploy (`npx vercel deploy --prod --yes`).
**Change the LLM model**: set `XAI_MODEL` (names from `GET https://api.x.ai/v1/models`) and redeploy.
**Deploy manually**: build data (see PROJECT_GUIDE section 7) then `cd site && npx vercel deploy --prod --yes && rm -f .env.local`.
**Force a site refresh now**: Actions -> Site -> Run workflow (optionally `sync_limit`).
**First image backfill**: run Site with `sync_limit=6000` once; afterwards hourly runs only add new ids.
**Add a column/table in Supabase**: add a migration file in `supabase/migrations/` and apply it (Supabase MCP `apply_migration` or SQL editor); keep RLS on. Public-read tables stay public; user Saved tables (`profiles`, `saved_items`, `saved_combos` in `20261103_user_saved.sql`) use `auth.uid()` RLS only.
**Enable Auth (Saved, site + mobile)**: in the Supabase project, Authentication → Providers: turn on **Email** and **Google**. For Google, create an OAuth client in Google Cloud (Web); paste the **callback URL shown on the Google provider page** in the dashboard (never commit that host). Redirect URLs: production `<origin>/auth/callback`, `http://localhost:4173/auth/callback`, and mobile `fancycash://auth/callback`. GitHub secret `SUPABASE_ANON_KEY` + variable `SUPABASE_URL` feed `site.yml` `--build-env` as `VITE_SUPABASE_*`. Vercel also has `VITE_SUPABASE_URL` / `VITE_SUPABASE_ANON_KEY` (config type — anon key is public by design). Locally: those Vite names in `site/.env.local`; mobile uses `EXPO_PUBLIC_SUPABASE_URL` / `EXPO_PUBLIC_SUPABASE_ANON_KEY` in `mobile/.env.local`.

**Base looks stale**: expected for a few days; the scraper's provisional matches cover the gap. A `data-stale` issue opens if canonical data is > 3 days old; the Site workflow warns only if both sources are old.
**Scraper broke (Source A layout change)**: see [SELF_HEALING.md](SELF_HEALING.md), run `cricket-data health --out diagnostics`; `auto-merge-scraper-fixes` merges fixes labelled `scraper-fix`.
**A workflow shows "workflow file issue"**: YAML error. `pip install actionlint-py && actionlint .github/workflows/*.yml`.
**A priced player shows no live numbers, or a wrong "Not in XI"**: the name could not be linked to the live source. Open the latest Site run's summary ("Player identity: names to review"), pick the right source player from the suggestions (or look the player up on the source) and add `<our id>,<source id>,<note>` to `data/mappings/player_identity.csv`; the next build applies it (and gives the player his source photo).
**A finished match's lines show no result, or a wrong one**: open the deployment's `/api/live` and look at `matches[].lines` of that match (`linked` in the body is how many ids the identity table holds; 0 means the table did not load and names decide). A wrong or missing value is a matching fix (identity CSV, above) or a `settleLines` fix: one server change, no browser change. Results already stored in `value_bets/archive/**/<fixture id>.json` (`results`) are never rewritten by a job: correct the value in that file by hand in a PR.
**Site shows no photos**: `data/photos.json` missing? (cache restored an old format: bump the cache key prefix in `site.yml`). Source A CDN down: the browser falls back to our Supabase copy / flags / silhouettes.
**Vercel deploy limits**: Hobby allows ~100 deploys/day; hourly = 24.

## Data guard failed the Site build
The "Data guard" step of `site.yml` (PROJECT_GUIDE 5.8) stops the job before the deploy when a hard invariant breaks, so the last good deploy stays up and nothing wrong ships. Open the run summary: the table names the check (a to g) and lists the matches at fault. The soft rows (warn) never stop a build; read them there. To reproduce: build the data (PROJECT_GUIDE section 7) and run `python -m cricket_site.guard --site site/public/data --data data`; `--now 2026-11-02T10:00Z` replays a moment. The live-body row needs the repository variable `SITE_URL` (the workflow reads `<site>/api/live`; with `DATA_WRAP_KEY` set it unwraps the body) and is skipped, never failed, when the body cannot be read. A failing hard check is fixed in the data or in the rule that made it (a stale `Live` row in `data/fixtures/upcoming.csv`, a duplicate fixture, an engine figure that no longer matches a recount), not by switching the step off; to ship an urgent change while the cause is fixed, run the workflow after correcting the data file.

## Mumbai relay (Feed G, Feed H)
Feed G's book refuses GitHub's US servers (403) but answers a server in India. `relay/` is a Cloudflare Worker (`relay/worker.js`, `relay/wrangler.jsonc`) placed near Mumbai (`placement.region` = `aws:ap-south-1`): it forwards one request to a host on its allow list and returns the answer, and refuses anything without its key. Upstream calls look like a Chromium browser in India (Accept-Language `en-IN`, Origin/Referer of the book host, Sec-CH / Sec-Fetch). Set as Worker secrets: `RELAY_KEY` (a long random string), `RELAY_ALLOW` (the first book's domains **and its odds-hub host**, comma separated) and `RELAY_ALLOW_EXTRA` (further books, same shape, so an extra book can be added without rewriting the first list). Set as repository secrets: `FEEDG_RELAY` (the Worker's address) and `FEEDG_RELAY_KEY` (the same key). With both set, `adapters/feedg.py` sends every request through the relay: the book sees an Indian Cloudflare edge address, whoever called the relay (checked from a GitHub US runner). Feed H **always** uses the same relay (its own `FEEDH_RELAY` pair, or Feed G's if those are already set): there is no direct call, and `fetch` is a no-op on a laptop (`GITHUB_ACTIONS` unset), so a home IP never reaches the book or the relay. Feed H's domain goes in `RELAY_ALLOW_EXTRA`. Deploy from `relay/` with Wrangler (or the Cloudflare dashboard). The Worker's own hostname is configuration, never committed. `?health=1` with the key returns the colo that answered (no upstream). Dispatch-only probes: `.github/workflows/feedh.yml` (Feed H counts) and `.github/workflows/feedg.yml` (Feed G `event_list` with a few Origin/Referer/UA/cookie variants, then the full adapter). If Feed G still 403s through a healthy Mumbai colo, the book is blocking Cloudflare datacenter IPs: use the India runner below.

## India runner (Feed G), the alternative
(Not needed while the relay works.)
Feed G's book answers GitHub's US servers with 403, so its read runs on a small server in an India region (not a personal computer) that is registered as a self-hosted runner with the label `india`. `.github/workflows/feedg-india.yml` runs only there, on a schedule and by hand (a pull request or push never reaches it, since the repository is public), and commits `value_bets/state/feedg_latest.json`; the hourly value-bets run uses that file when the book refuses it (at most `CV_FEEDG_STATE_MAX_HOURS`, default 3, old, and only for matches that have not started).
1. Create the server (Ubuntu 24.04, 1 GB is enough, SSH key only) in an India region, e.g. DigitalOcean Bangalore.
2. `sudo apt-get update && sudo apt-get install -y python3-venv git`.
3. GitHub: Settings, Actions, Runners, New self-hosted runner, Linux. Run the download and configure commands it shows on the server, with the label `india`, then `sudo ./svc.sh install && sudo ./svc.sh start`.
4. When the runner shows Idle, set the repository variable `FEEDG_INDIA_RUNNER` to `on` (Settings, Secrets and variables, Actions, Variables). Set it back to anything else to switch the job off. Until it is `on` the job is skipped, not queued.
5. Run "Feed G (India runner)" once by hand and check that `value_bets/state/feedg_latest.json` is committed; the next value-bets run then lists Feed G as ok.
The book may also refuse a cloud server's address: then the manual run fails with 403 and the server can be deleted. Nothing else depends on it.

## Analytics
The site counts page views and a few button taps with Vercel Web Analytics (`@vercel/analytics`, MIT, free tier, no cookies, no personal data, so no consent banner). The script is added in `site/src/main.tsx`; events go through `site/src/lib/analytics.ts` (`player_filter`, `share`, `books_open`, `fancy_market`) and are forwarded to GA as well. To read the host dashboard, turn on **Analytics** once (Project, Analytics, Enable); nothing is collected until then. Events with properties need the Pro plan to be filtered there; the free plan counts page views and shows custom events as totals. The SPA catch-all rewrite skips `/api/` and `/_vercel/` so the insights script is not swallowed.

Google Analytics 4 loads the same way when `VITE_GA_MEASUREMENT_ID` is set (`site/src/lib/ga.ts`): the Google script loads only after the first click, key press, scroll or touch (events queue until then), and never in an automated browser, so a bot that just loads the page is not counted (a cloud-hosted headless browser had been 12 of 17 "new users"); no cookie banner, ads cookies denied, SPA `page_view` from `App` with referrer, UTM, device, OS, language and an `is_bot` flag (headless Chrome, webdriver, known crawler UAs — so a Linux browser from an edge POP is tagged separately from a person). `/api/geo` reads the edge country/region headers (host and Cloudflare) and sets them as user properties. The measurement id is a GitHub secret, inlined at build; it is never in source. Without the secret the tag is not injected. Country/city tables in GA fill after a few hours of traffic; empty breakdowns before that are the property being new, not a missing tag.

**Errors and speed.** Page errors are counted as events named by kind: `error_chunk` (a script of an older deploy was gone; the page reloads itself), `error_render` (a page threw, the Reload button showed), `error_script` and `error_promise` (anything else), at most five per page load, so the totals read on the free plan (the message and page go along as properties, readable on Pro). Loading speed (Core Web Vitals per page) comes from Vercel Speed Insights (`@vercel/speed-insights`, Apache-2.0, free tier): turn on **Speed Insights** in the same project dashboard. Watch for a rise in `error_chunk` right after a deploy (normal, small) and any `error_render` (a bug).

## Match state (one phase per match)
A **Cloudflare Worker** (`state/worker.js`, `state/wrangler.jsonc`, Cron Trigger every minute: GitHub's own cron slips by minutes, so it is not used for this) reads the live feed with the same code the site uses (`site/packages/engine/feed.js`) and writes `public.match_state` (migrations `supabase/migrations/20261031_match_state.sql` and `..._writer.sql`) through the database function `apply_match_state(token, upserts, phases)`: one row per match, rows the feed dropped settled by the clock (in play for the keep window, 24 h or 6 days for a Test, then final). The writer holds only the project's **public** key plus a random write token whose SHA-256 is stored in `private.match_state_writer`; the service key is not involved and the table cannot be written any other way with the public key.

`site/api/state.js` serves the table in the shape of `/api/live` `matches[]`; the player page's match card uses it after the live feed and before the clock (`matchPhase`), and only while the table's last write is under 20 minutes old (`freshState`).

| Name | Where | Used by |
|---|---|---|
| `LIVE_SOURCE_BASE`, `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `STATE_WRITE_TOKEN` | **Cloudflare Worker secrets** (`wrangler secret put`, in `state/`) | the writer |
| `SUPABASE_URL`, `SUPABASE_ANON_KEY` | Vercel env (Production and Preview) | `api/state.js` (read-only) |

Deploy: `cd state && npx wrangler deploy`. Rotate the write token: generate a new random string, `update private.match_state_writer set token_hash = encode(extensions.digest('<token>', 'sha256'), 'hex')`, then `wrangler secret put STATE_WRITE_TOKEN`. By hand: `STATE_WRITE_TOKEN=... node site/scripts/state-sync.mjs`, or `curl -H "x-state-key: <token>" https://match-state.<account>.workers.dev` (runs one sync now and answers `{ok, listed, settled, written}`; without the key it is a 404; also usable by an uptime monitor). Check: `select phase, count(*) from match_state group by 1;` and `select max(updated_at) from match_state;` (under two minutes old). Logs: Cloudflare dashboard, Worker `match-state`, Observability. Without the table (not configured, or stale) the site works the phase out itself, as before.

## Telegram channel alerts
The same Worker run (`state/worker.js`, every minute) also posts to the Telegram channel, in stats wording (no stake sizes, no "bet" or "tip" language: the site's Terms say it does not offer, promote or encourage gambling). Three kinds, all built by `site/packages/engine/alerts.js` and posted by `alert-post.js`:
* **High-odds line cleared**: a priced player line (settled by `settleLines`) or a fancy line (`fancyStanding`) of a match in the live feed whose verdict is Cleared and whose best over price is 2.50 or longer (`HIGH_ODDS` in `tape.js`, the site's "High odds hits"). One message per match per run, up to 8 lines; each line is announced once however long it stays cleared.
* **Model edge**: each alert in `value_bets/out/new_alerts.json` (the hourly pipeline's new value bets, read from GitHub raw) for a match that has not started: edge, the price a book lists, the model's fair price and its reason. The pipeline's stake figure is never sent.
* **Fancy edge** (before the match): each alert in `value_bets/out/fancy_alerts.json` (see "Fancy edge alerts" below) for a match that has not started: edge, market, line, the best listed price, how often the side has gone through in the recent matches, and the history chance.
Not alerted: low-odds misses, match winner.

**Fancy edge alerts: how the edge is computed.** Nothing server-side priced fancy lines before, and the Worker has no match history (the built site data does not exist inside it), so the edge is computed in an hourly workflow and the Worker only posts the file. The **Value bets** workflow (hourly, round the clock; it already commits `value_bets/out`) builds the site data right after the pipeline has refreshed `book_lines.json` (`python -m cricket_site.build` into a temporary folder, the same build the Site workflow runs minus photos; the Base download is cached per day under its own key `fancy-dl1-<date>`), then runs `node site/scripts/fancy-alerts.mjs`, which writes `value_bets/out/fancy_alerts.json` (committed with the other outputs; `generated_at_utc`, the bar used, and `alerts`). The scoring is the **same code as the site's Match Fancy tab and `/fancy` cards**: `site/packages/engine/fancy-edge.js` (`marketRow`, `fancyOverview`, `fancyInputs`; the React view calls it too, so the two cannot drift), i.e. `sideEdge` in `stats.js`: the side's hit rate over the two teams' last 20 matches in the format, pulled toward the market's no-vig chance as ten extra games, times the best listed price, minus 1 (docs/SITE.md, "Edge"). Nothing comes from a model. An edge is announced only when all of these hold (`ALERT` in `fancy-edge.js`, unit-tested with hand-computed numbers in `site/tests/fancy-edge.test.mjs`): the match has not started and the schedule gives its time, both sides are in the data, the better side's edge is **at least 15%**, **at most 60%** (an edge that large nearly always means a stale line or rules the history was not scored on, so it is held back), and it comes from **at least 15 played games** (the site shows an edge from 10; a line that voids when a side bowls first is scored on the matches that side batted first, so its sample is the smaller one). The three biggest per match are written. This is history only: nothing models the ground, conditions, team news or the matchup except through the market's price, and a book can list a line that means something the history was not scored on, so the channel text says "past data, not advice" and gives the sample size ("under in 16 of 20 recent matches").

Each alert's `alert_id` is the schedule's fixture id plus market, team, innings and **side** (not the line): a line that moves is the same alert, announced once however its price drifts. The Worker reads the file from GitHub raw next to `new_alerts.json`, skips a file older than 12 hours (the workflow step has stopped, so its prices are stale; the overnight gap between runs is 10 hours) and any match that has started, claims each key in the same table as the other kinds (key `fancy|<alert_id>`), and posts at most 4 messages a run. If the step fails (no Base download, build error) the workflow still commits the pipeline's outputs and the last alert file stays; failed steps show as a warning on the run.

**Once only.** Every alert has a key; `claim_alerts` (migration `20261101_alert_sent.sql`, same write token as the match-state table, no new secret) marks it sent atomically before the post, and a post that fails is handed back with `release_alerts` so the next minute tries again. No table, no posts. At most 4 messages go out per run, so a backlog drips out instead of flooding the channel; a 429 from Telegram stops the run.

**Set up (you do these; the token is never pasted into chat, a file or a commit):**
1. In Telegram, talk to @BotFather: `/newbot`, pick a name, copy the token. Then add that bot as an **administrator** of the channel with the "Post messages" right.
2. Apply `supabase/migrations/20261101_alert_sent.sql` to the project (SQL editor or `supabase db push`).
3. Set Worker secrets: `cd state && npx wrangler secret put TELEGRAM_BOT_TOKEN` and `npx wrangler secret put TELEGRAM_CHAT_ID` (the channel's `@username`, e.g. `@yourchannel`; a private channel uses its numeric id). `SITE_URL` (the public site address, no trailing slash) is what gives the posts a picture and an "Open the site" link: a message with a player line goes out as a photo (that player's share card, `/card/v9/pid/<id>/<stat>/<line>.jpg`, the same picture a shared link shows) with the text as its caption; fancy-only messages and messages without the variable are text. Telegram fetches the picture itself, so if it cannot the text goes out alone. Then `npx wrangler deploy`.
4. Check before it posts anything: `curl -H "x-state-key: <STATE_WRITE_TOKEN>" "https://match-state.<account>.workers.dev/"` runs one sync and **previews** the alerts: `alerts.messages` is the text that would be sent, nothing is sent or marked, and it works before the bot exists. `?alerts=post` posts now, `?alerts=off` skips them.
Without `TELEGRAM_BOT_TOKEN` and `TELEGRAM_CHAT_ID` the scheduled run posts nothing and reads no alert file. To stop posting: delete those two secrets (`wrangler secret delete`). Telegram allows about 20 messages a minute to one chat; the cap above stays well under it.

**What belongs on Cloudflare rather than GitHub Actions:** anything on a clock tighter than about 15 minutes (GitHub cron is best-effort and a public repository's schedules are paused after 60 days of no activity) and anything whose source refuses GitHub's US runners (the Mumbai relay already). Heavy batch work (the Python data build, image sync) stays on GitHub.

## Scheduler Worker (the data workflows' clock)
**Why.** GitHub's cron is best-effort. Measured on 2 Nov 2026 with `gh run list --event schedule`: the "every 30 minutes" scraper ran 1 to 6 hours apart, and the hourly value-bets and site workflows and the two-hourly ball-by-ball workflow were just as late or skipped. A Cloudflare Cron Trigger fires on the minute, so `scheduler/` (Worker `dispatch-scheduler`: `worker.js`, `slots.js`, `wrangler.jsonc`) starts those workflows itself.

**What it does.** Every minute it works out, per job, the latest slot that has started (`slotStart` in `scheduler/slots.js`; the cron strings are the ones each workflow keeps in its own `schedule:`, and a test checks they agree). Times are UTC:

| workflow | slot |
|---|---|
| `scraper-update.yml` | minutes 7 and 37 of every hour |
| `value-bets.yml` | minute 30 of every hour, all 24 hours |
| `site.yml` | minute 50 of every hour |
| `balls-update.yml` | minute 47 of every second hour (00, 02, ... 22) |

For each job it reads the workflow's latest runs (`GET /repos/<repo>/actions/workflows/<file>/runs?branch=main&per_page=5`; pull-request dry runs are ignored, they commit nothing) and **skips** when a run was created since the slot began (GitHub's own cron firing late never doubles a run) or when one is queued or in progress (a run still "running" after 2 hours is stuck and does not block). Otherwise it starts the workflow: `POST .../dispatches` with `{"ref":"main"}` and the token as `Authorization: Bearer`. A slot that is handled costs no further calls; a failed call is retried after 5 minutes; one job failing never stops the others, and the cron handler never throws (it logs and counts). A late run still gets its slot: if the previous run is still going when a slot starts, the dispatch follows as soon as it has finished.

Left alone: `feedg-india.yml` (self-hosted runner), the daily 03:17 scraper backfill and the weekly value-bets refit (they stay on GitHub's cron; a dispatch is a plain 30-minute or hourly run). The workflows' own `schedule:` crons stay as the fallback; if both fire in one slot the second is just another run in the workflow's `concurrency` group (GitHub keeps only one *pending* run per group, so a newer pending run replaces an older one; `scraper-update.yml` and `balls-update.yml` share a group). A dispatched `scraper-update.yml` run does not run the sitemap health check (new input `health_check`, off by default; the daily run still does).

**Set up (you do these; the token is never pasted into chat, a file or a commit):**
1. Deploy: `cd scheduler && npx wrangler deploy`. Until the secret exists every tick logs "GITHUB_DISPATCH_TOKEN is not set" and does nothing. `GITHUB_REPO` (`owner/name`) and `DISPATCH_REF` are in `scheduler/wrangler.jsonc`; change them for a fork.
2. GitHub -> Settings -> Developer settings -> Fine-grained personal access tokens -> Generate: repository access **Only select repositories** = this repository; Repository permissions **Actions: Read and write** (nothing else; Metadata read is added automatically). Choose an expiry and note the date.
3. `cd scheduler && npx wrangler secret put GITHUB_DISPATCH_TOKEN` and paste the token at the prompt.
4. Check `/status` (below) within two minutes. When the token expires or is revoked, `last_tick.error` shows `HTTP 401` and GitHub's own cron carries on as before; make a new token and repeat step 3.

**See it working.**
* `curl https://dispatch-scheduler.<account>.workers.dev/status`: per job its `cron`, the current `slot` and the `next_slot`, `last_tick` (what this Worker instance last did: `dispatched`, `skipped` with `run-in-slot` or `running`, or `failed` with the error), and `last_dispatched_run` / `latest_run` as GitHub lists them (`created_at`, `event`, `status`, `conclusion`). `token` says `set` or `missing`; no secret is in the answer. Cached for 30 s; the instance counters restart when Cloudflare restarts the instance.
* Cloudflare dashboard -> Workers -> `dispatch-scheduler` -> Observability: a `scheduler: {...}` line for every dispatch and failure.
* GitHub: `gh run list --workflow value-bets.yml --event workflow_dispatch --limit 5`; the Worker's runs start within a minute of the slot.
* **Is the gap closing?** `node scheduler/measure.mjs --days 3` (uses the signed-in `gh`; add `--from 2026-11-02T00:00Z --to ...`, `--json`, `--repo owner/name`). For each workflow it takes every complete slot in the window and the first run created inside it: `slots`, `run` (slots that got one), `missed`, `<=5m` (started within 5 minutes of the slot), `p50`/`p90`/`max` lag in minutes, `gap h` (longest time between two runs) and `first run by` (`schedule` = GitHub's cron, `workflow_dispatch` = this Worker). Run it for a window before the deploy and for one after. The raw version: `gh run list --workflow scraper-update.yml --event schedule --limit 30 --json createdAt`.

**Turn it off.** `cd scheduler && npx wrangler secret delete GITHUB_DISPATCH_TOKEN` makes every tick a logged no-op (keeps the Worker, `/status` says `missing`); `npx wrangler delete` removes the Worker; revoke the token under GitHub -> Settings -> Developer settings. Nothing else needs changing: the workflows' `schedule:` crons never went away.

**Limits.** Free Cloudflare plan: 1,440 cron invocations a day plus `/status` calls (the plan allows 100,000 requests a day), at most 8 GitHub calls per tick (the limit is 50). GitHub API: about one list call per job per slot, plus one a minute while a run is in progress, far under the token's 5,000 an hour. `/status` is open to anyone with the Worker's address (it holds no secret; set `workers_dev` to `false` in `wrangler.jsonc` to hide it). The Vercel Hobby deploy limit (about 100 a day) is not at risk: `site.yml` is dispatched at most 24 times a day.

## Scraper protection
`/data/*` is wrapped (key from `/api/gate`, never in the bundle) and behind the gate cookie. The gate and `/data` answer only requests from our own page (`Sec-Fetch-Site`, `site/packages/engine/guard.js`), refuse self-identified scrapers by User-Agent, and `robots.txt` asks AI crawlers to stay out (`AI_CRAWLERS` in `build.py`). None of this stops a script that runs the whole app in a real browser: the browser must be able to read the data to draw it.
