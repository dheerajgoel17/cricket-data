# The iOS / Android app (`mobile/`)

Expo (React Native, TypeScript), one codebase, two store builds. Free, no accounts: saved state stays on the device (MMKV through `@cricket/storage`). Agent rules: `mobile/AGENTS.md`.

## What is shared with the site, what is not
* **Shared, imported from `site/` (see `mobile/metro.config.js`, `tsconfig.json`):** `@cricket/engine` (all numbers and rules), `@cricket/storage`, `@cricket/tokens` (colours come from `tokens.json` as they are), and pure files from `site/src/lib`: `priority.ts` (rail ranking), `home-phase.ts` (In play / Pre-match / Resulted), `assets.ts` (flag URLs), `hot-lines.ts` (which lines Hot props scores, their order), `books.ts` (book logos) and `format.ts` (odds, short venue names).
* **Not shared:** components, pages, hooks. The UI is React Native (`mobile/src/ui`, `mobile/src/app`); sizes keep the web's role names with native values (`src/ui/tokens.ts`).
* **Copied, to be moved into the engine:** these mirror React code that cannot be imported, so a change to the original needs the same change here until Phase 1 moves the logic into `site/packages/engine` and both import it: `src/lib/rail.ts` (`usePricedFixtures` in `site/src/hooks/useEngine.ts`, `useHomeRail`, and the phase counts of `site/src/pages/Home.tsx`) `src/lib/card.ts` (`FixtureCard` in `site/src/components/app/fixture-card.tsx` and `playState` in `site/src/lib/play-state.ts`: live / started / delayed / final, scores, status line; a started match has no LIVE badge and says the source has no score), `src/lib/hot.ts` (`useHotRows` in `site/src/components/app/hot-props.tsx`: the scoring loop around the engine; `useTick` / `StandingMark` in `src/ui/tick.tsx`) `src/lib/fancy.ts` (`useFancyCards` in `site/src/hooks/useFancyCards.ts`) and `src/lib/player.ts` (`PlayerScreen`, `nextMatch` and the chart numbers in `site/src/pages/player.tsx`; `deriveChart` is pure and tested).

## Data path
The app reads the same files as the site: `/data/*.json` and `/api/live`, through the data gate.
* `GET /api/gate` returns the cookie and the unwrap key (`X-Cd-K`). The app sends the cookie header by hand (no browser cookie jar) and refreshes it on a 403 (`mobile/src/lib/net.ts`).
* Every request carries its own user agent (`FancyCash/<version> (<os>)`). Android's default one (`okhttp`) is on the gate's block list and is refused everywhere. The gate today lets in any client that is not on that list and sends no `Sec-Fetch-Site`; that is a speed bump, not a lock, so a key kept in the app would not be one either. If the gate is tightened, give the app its own explicit way in rather than a browser-looking user agent.
* The small files (fixtures, photos, identity) and `/api/live` arrive wrapped (`engine/wrap.js`: SHA-256 keystream). The unwrap needs `TextDecoder` and `crypto.subtle.digest`, which Hermes lacks; `src/lib/polyfills.ts` supplies both (SHA-256 from `@noble/hashes`, MIT, synchronous, because the unwrap hashes one small block per 32 bytes and a native call each would be thousands per poll). It is installed first, from `mobile/index.js`. The digest hands the main thread back after 8 ms of work (`FRAME_MS`), so a big file does not hold the screen.
* The site URL is `EXPO_PUBLIC_SITE_URL` in `mobile/.env.local` (ignored). It ends up in the built app, never in a tracked file.
* The stats engine's data (`src/lib/data.ts`): `meta.json`, `index.json` and `matches.json` (about 4.5 MB) load once, then a player's own file (`p/NN.json`, 0.5 MB) when a row needs it. Hot props scores one day's priced lines against those files (`src/lib/hot.ts`, `use-hot.ts`).
* Team crests are the source's logos from `photos.json` (`teamLogos`), else the national flag (`flagUrl`), else initials, as on the site.

## Look
The Home tab follows the site's phone Home: the brand header, 80%-width snapping fixture cards (state and format, crests, scores or start time, status line, series, Props — Test stumps use `sessionBadge` / `nextTestDayLine` from the engine via `cardModel`, same as the site), the floating In play / Pre-match / Completed tabs (no series chips on the rail), and the six tabs (Fixtures, Player props, Fancy, Leagues, Saved, Contact). Colours come from the shared tokens; type is the site's pairing: Satoshi for text and titles, Barlow Condensed for 11 pt caps labels and all numbers (`font`, `cap`, `num` in `src/ui/tokens.ts`), loaded in `app/_layout.tsx` with the splash held until they are in. Below the rail: the market tape ("High odds hits" / "Low odds misses") and **Props**, fixture hashtags (`MatchChips`: overlapping bare crests in one ring + `ABR v ABR`, matching the site's MatchChip / AvatarGroup) then a mixed player+fancy list for the chosen match (`mixHomeRows` in `site/src/lib/hot-lines.ts`: rank by `hotOrder` first, rebalance only outside a ~⅓–⅔ band; today+tomorrow player lines scored so a tomorrow chip is not fancy-only; Player props and Fancy links in the header). Empty lists use the same `EmptyState` pattern as the site (title + body on a tonal surface). Prop rows and fancy Overview rows share the same chrome (condensed line, books, model edge without a pill box, MiniBars). The Player props tab lists the day's rows with the same prop row, a day chip row (Today, Tomorrow, then dates) and pull to refresh on both platforms (`RefreshControl`). Crests and player kit images use Expo Image `memory-disk` cache. Motion: pulsing LIVE dot, cards and rows rise and fade in (fewer staggered rows on Android to hold 60 fps), pulsing placeholders while lines are scored, price and so-far flashes with an arrow when they move. Horizontal hashtag scroll: iOS `decelerationRate=fast`, Android `removeClippedSubviews` + no overscroll glow. Native components wherever there is one: the system tab bar, `Segmented` (SwiftUI picker on iOS, Compose segmented buttons on Android: Over / Under, format, innings, In play / Pre-match / Resulted, Lines / Game log / Splits), and system form sheets for the info popovers (`app/info/[topic].tsx`, topics in `lib/info.ts`). Page headers and the filter bars are `BlurBar`s over the scroll view (a `BlurTargetView`); the sub-bars (format, innings) collapse as you scroll down (`useCollapseOnScroll`). Filters, alt lines and splits are accordions (`ui/accordion.tsx`, height and chevron animated on the UI thread). Loaders (`Working`) are centred in their section or page. The tab icons are the site's Ionicons, drawn as images (`assets/tab-icons`, made from the `ionicons` package). To compare with the site, run the browser preview (below) next to the live page at 375 px: the counts and the first chips are the same.

## Pages
The root is a stack with the tab group on the bottom (`src/app/_layout.tsx`, `(tabs)/_layout.tsx`); a page one level down is pushed over the tabs and has the reference app's header (`ui/page-header.tsx`: a round back button, the name and what it is centred, round Save / Share buttons at the right) and the system swipe-back. Taps (`src/lib/nav.ts`): a fixture card opens `/fixture/<id>`; a prop row or a market-tape row opens `/player/<index>?stat=&line=&fmt=&scope=` (the site's own parameters, plus `team`); "See all" opens the Player props tab.
* **Fixture page** (`app/fixture/[id]/index.tsx`): the match in a container (`ui/match-header.tsx`) and the site's four sections as a native segmented control: **Props**, **Match Fancy**, **Grid**, **Custom line** (was Trends). Props and Match Fancy only show when the books price them. A first-class match says it has no player props. Share sends the match text and link.
* **Match Fancy** (`ui/match-fancy.tsx`): scope chips (Match / each side) beside a Filters button (`L{n}`, default L10 like the site) that opens a sheet for the hit-rate window and Teams' form / At ground — same pattern as Props. Match-scope L10 is the newest 10 among either side's last 10 (`fancySample`); switching Match / NZ / IND keeps the peer market (`peerFancyFm`, e.g. Fours stays Fours) and the O/U line when still priced. "Bookmaker lines" ranked by edge; tapping a row opens `/fixture/<id>/fancy?fm=&sc=` (`app/fixture/[id]/fancy.tsx`), a dedicated market page with the median, chart, over/under, ground note and line ladder (like a player page). Match-level rows use a chart icon; team rows keep the crest. Ground note on each row is `N/M under at Eden Park` (`shortVenue`). Old `?tab=fancy&fm=` links redirect to the market page.
* **Grid / Custom line** (`ui/grid-table.tsx`): stat chips beside Filters (`L{n}`); the custom line, games window and (on Custom line) the minimum hit rate sit in the sheet. Grid team switch is chips. Grid: players down, last fixtures across, tinted by distance from the line. Custom line: players who clear the line often enough.
* **The live match** (`ui/live-board.tsx`): while a match is on, the pair at the crease with their partnership, the last wicket, the bowler, this over's deliveries and the run rates; under the match two closed rows, **Scorecard** (innings picker, batting and bowling tables, fall of wickets, yet to bat; so far only, never used for settlement) and **Recent form** (each side's last results, `ui/recent-form.tsx`, `lib/form.ts`). A finished match whose lines the live feed has let go is read from its permanent archive file (`lib/archive.ts`, the address in `EXPO_PUBLIC_ARCHIVE_URL` in `.env.local`), so a link to an old match still shows its props.
* **In-play lines** (`lib/use-lines-live.ts`, `lib/merge-live.ts`): the books file with the started matches' live lines folded in by the engine's `liveMerge`, the same merge as the site's `useLinesLive`; `/api/inplay` (`inplayQuery`) is polled every ~15 s only while a priced match is on. Props, Match Fancy, the Fancy tab and the fixture page read it instead of the plain file, so a row whose line is a live price gets the red **Live** mark, "was N" (where the line opened), the progress bar (`ui/live-bits.tsx`, geometry in `lib/live-track.ts`) and the "From here" counts (`ui/live-spot.tsx`: batter's own history, similar in-play lines, similar team innings). Live markets that are not a batter's runs or a side's total are prices-only rows at the end of Match Fancy (`ui/live-market-row.tsx`). Rows are scored again when the live lines change (`live_sig` is in the cache keys).
* **Synced with the site (2026-11-12):** Test props and fancy carry the site's tags ("1st innings", "2nd innings", "Complete match", "If bats first": `scopeTag`, `innTag`, `BAT_FIRST_TAG`); a live fixture's page opens on one `ScorecardCard` (header, batters, bowler, over, "Full scorecard" in place, `ui/live-board.tsx`) and the Scorecard accordion shows only when the match is not live; a live line is a row of its own beside the pre-match one (`isLive` in the row key and in `scoreHotRows`) and live-priced rows are exempt from the history minimum; the Home rail reads `config/home_rail.json` at view time (`railConfigQuery`, `sanitizeRail`), the built-in order when it cannot be read. Fixture cards and the match header are a plain `color.card` surface; the loading placeholders are shaped like the card and a prop row (`CardSkeleton`, `RowsSkeleton`) and the Props block shows its own placeholder while the rail loads.
* **Fancy tab** (`app/(tabs)/fancy.tsx`, `lib/fancy.ts`): every priced match not yet over with its best-edge markets (the book's line, the edge, the last ten results as bars, venue hit rate, the other books behind "+N books"), in the Home rail's order; tapping a market opens `/fixture/<id>/fancy` (the market page), the card header opens the fixture's Match Fancy list. Matches are scored one at a time with the main thread given back in between.
* **Leagues tab and competitions** (`app/(tabs)/leagues.tsx`, `app/competitions.tsx`, `app/league/[id].tsx`, `ui/tournament-stats.tsx`, `lib/league.ts`): the league chips (live and soon first, Big Bash on top), then the season picker, the season in four numbers, the leaders rail, Batting / Bowling / Overall lists (best five, "Show all") and the season-by-season bars. "More" opens the competition (Stats, Markets, Teams, Results); "All competitions" lists every one with eight matches or more.
* **Team page** (`app/team/[idx].tsx`): format, then Player grid (stat, line and games), Markets (the engine's match markets over the team's matches, a ladder for each) and Top batter (the team batting first); the star saves the team.
* **Saved tab** (`app/(tabs)/saved.tsx`): free sign-in (Google or email via Supabase Auth, same tables as the site). Watchlist / players / teams sync server-side; recently viewed stays on device. Set `EXPO_PUBLIC_SUPABASE_URL` and `EXPO_PUBLIC_SUPABASE_ANON_KEY` in `mobile/.env.local` (never commit). Add redirect `fancycash://auth/callback` in Supabase Auth URL config for Google. **Search** (`app/search.tsx`, the button in the header): players (typo tolerant), teams, matches and leagues; empty, it offers the tabs and the last players opened.
* **Player page** (`app/player/[idx].tsx`, logic in `lib/player.ts`), in the site's order: the stat switch and the format / innings segmented rows (the last two tuck away on scroll); the player's name, team and picture (kit, crest and hero team label follow the match side via `matchSide`, same rule as the site — including `?line=` / `?start=` so a club List A and an international of the same format do not steal each other's shirt; profile team only when there is no match); hit rate gauge with hit rate, fair price, last-20 average and the line, and the prop / opponent strip; Over / Under, the line stepper (one capsule: minus, the line, plus) and the watchlist star; "Alt lines" (every line the books price, edge on each); the bar chart with the line, values in the bars, date and opponent under every bar (every other one past ten games) and the look-back windows with their hit rates beside a round filter button; the next match in a container (start time or LIVE or Completed, the line with whether it cleared and the best price, the books' table, two tiles with his rate at the ground and against that side; no inline how-to note); opponent/ground quick picks sit at the top of the Filters accordion (opposition, venue, home / away, batted first / chasing, position, level, last games; they re-run the engine plan); at a glance (cleared, hit rate, fair price in one card), and Lines (the ladder with the chart's line highlighted, and "when it hits") / Game log (a tap opens the game) / Splits tabs. Tables fit the screen width (`DataTable` weighs its columns, `Pill` keeps a column of tinted figures aligned); none scrolls sideways. The games come from the engine once per stat and format; moving the line only recomputes the rates.

## Glass
Dark only. iOS: the system tab bar (`expo-router/native-tabs`) and `GlassView` (`expo-glass-effect`), which are liquid glass on iOS 26 and later and a system blur before. Android has no system glass: the tab bar is ours, a `BlurView` (`expo-blur`) over the screens' `BlurTargetView`, and the target must not contain the blurring view. Surfaces inside the screens on Android are a solid tint. See `src/ui/glass.tsx`, `src/components/app-tabs*.tsx`.

## Run it
```bash
cd mobile && npm ci
printf 'EXPO_PUBLIC_SITE_URL=%s\n' "$SITE_URL" > .env.local     # the site's address, from site/.env.local
npm run typecheck && npm test
npm run web              # browser preview on :8082 (react-native-web); Metro proxies the site (dev-proxy.js), no gate or cookie needed in the browser
npx expo run:ios          # full Xcode, selected with xcode-select
npx expo run:android      # JDK 17 (JAVA_HOME) and the Android SDK (ANDROID_HOME) with an emulator or phone
```
The preview shows layout, type and data, not the native glass or the iOS system tab bar. The browser preview and Android share the floating capsule footer (`FloatingTabBar` in `app-tabs.web.tsx` / `app-tabs.android.tsx`). Android native is not being rendered for now; the code and the build are kept working. Contact is the sixth tab (`(tabs)/contact.tsx`), mailto to tech@fancy.cash like the site.
`android/` and `ios/` are generated by `expo prebuild` and not committed.

## Performance
Stay on Expo/RN; speed comes from less JS work and virtualized lists, not a native rewrite.

### Start-up (2026-11-05)
Measured with `EXPO_PUBLIC_PERF=1` (see "Measuring start-up" below). Where the time went on the iOS simulator, debug build, before this pass: the schedule and lines were behind a wait for every other tab to mount; `matches.json` (about 9 MB) was over the body cache's 6 MB cap, so every launch downloaded it again (`r.text()` alone held the JS thread for 1.5 s); each of the ~16 player files cost a conditional request even when nothing had changed; the scored rows were thrown away between launches, so every launch scored ~280 lines again (6 to 8 s of JS, a third of it deliberate sleeping); and the live poll rebuilt the rail three times over.
* **Scored rows kept on the device** (`lib/hot-cache.ts`, wired in `lib/use-hot.ts`): a day's rows are saved when a pass finishes. A snapshot from the books file's current generation is the answer (nothing is scored); an older one (under 3 hours) paints at once and is replaced when the fresh pass lands.
* **Stats files pinned to the data build** (`lib/net.ts`, `lib/body-cache.ts`, `lib/data.ts`): `meta.json` (always asked for, 358 bytes) says which build is current; index, matches, identity, names and the player files kept under that same build are read from the device with no request. A new build revalidates them as before (304 or a new body). The body cache cap is 24 MB, so `matches.json` is kept too.
* **Home paints from the last launch's schedule and lines** (`lib/queries.ts`: `initialData` from the kept copy when under 3 hours old, counted stale so the real one is asked for at once). The stats data then loads after the first screen; it starts as soon as the rail is ready (`use-rail.ts`).
* **Tabs mount when first chosen** (`ui/lazy-tab.tsx`): the native tab bar mounted all six at launch, so Props, Fancy, Leagues, Saved and Contact rendered and started their own queries while Home was loading.
* **Scoring** (`lib/hot.ts`): matches already on are scored first (`lib/hot-priority.ts`), the first row is published at once (then every 600 ms), the loop sleeps 4 ms per 8 ms of work (was 12 per 6), and the lines are grouped by match once instead of filtered for every line.
* **Cheaper live poll**: the rail is built once per set of inputs and shared by Home, Props and Fancy (`use-rail.ts`), a fixture's state is worked out once per build (`rail.ts`), the books' fixtures once per books file, the model projection once per row (`model-side.ts`), and `PropRow` is memoized on its row and live standing, so a poll that moved another match leaves it alone.
* The splash holds for at least 1.1 s (was 1.6 s): the drawing finishes in about a second.
* **Published hot rows (2026-11-12, PROJECT_GUIDE 5.11):** the builder step `site/scripts/hot-rows.mjs` writes the history of every priced line to `/data/hot-rows.json`; `lib/queries.ts` `hotRowsQuery` reads it when its `build` equals `meta.json`'s, and `scoreHotRows` (`lib/hot.ts`) turns every covered line into a row at once (`seedRow`, the prices are the phone's own books) and scores only the rest, asking for the store and the player files (`loadStore`) only then. Done on the server: the scoring. Not done: splitting the innings table (`inn`, over half of `matches.json`) out of the file the engine loads first.
* Earlier passes: Props and Fancy use FlashList; unwrap yields every 8 ms; body cache + ETag 304; polling follows app focus (`watchAppState`); wrapped responses whose ciphertext matches the kept fingerprint skip unwrap and unchanged bodies reuse the same object, so a poll with no change re-renders nothing (`lib/net.ts`, `lib/body-cache.ts`).

### Measuring start-up
```bash
cd mobile && EXPO_PUBLIC_PERF=1 npx expo start --port 8081      # a debug build on the simulator loads from it
xcrun simctl terminate booted cash.fancy.app && xcrun simctl launch booted cash.fancy.app    # warm: the app's storage is kept
```
Cold is the same with the app's `Documents/mmkv` folder in its data container removed first. `lib/perf.ts` prints `[perf] <mark> <ms since the bundle started>` (fonts-ready, rail-ready, first-fixture-card, first-props, scoring-done, fancy-ready, splash-done, store-ready), `[perf-span]` for each network read (net / body / unwrap / parse) and any slice of work over 15 ms, `[perf-render]` for React commits over 12 ms, and `[perf-stall]` / `[perf-jank]` for stretches where the JS thread did not answer a 100 ms timer (a lost frame or more). The same lines are also kept in storage (`perf-log`), because a release build prints nowhere you can read. Nothing runs without the flag.
