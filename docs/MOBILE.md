# The iOS / Android app (`mobile/`)

Expo (React Native, TypeScript), one codebase, two store builds. Free, no accounts: saved state stays on the device (MMKV through `@cricket/storage`). Agent rules: `mobile/AGENTS.md`.

## What is shared with the site, what is not
* **Shared, imported from `site/` (see `mobile/metro.config.js`, `tsconfig.json`):** `@cricket/engine` (all numbers and rules), `@cricket/storage`, `@cricket/tokens` (colours come from `tokens.json` as they are; space / type / radius / control are derived in `src/ui/tokens.ts`), and pure files from `site/src/lib`: `priority.ts` (rail ranking), `home-phase.ts` (In play / Pre-match / Resulted), `assets.ts` (flag URLs), `hot-lines.ts` (which lines Hot props scores, their order), `books.ts` (book logos) and `format.ts` (odds, short venue names).
* **Not shared:** components, pages, hooks. The UI is React Native (`mobile/src/ui`, `mobile/src/app`). Web and app catalogues, the compatibility map (mirrors vs native twins), and screen coverage: [DESIGN_SYSTEM.md](DESIGN_SYSTEM.md).
* **Copied, to be moved into the engine:** these mirror React code that cannot be imported, so a change to the original needs the same change here until Phase 1 moves the logic into `site/packages/engine` and both import it: `src/lib/rail.ts` (`usePricedFixtures` in `site/src/hooks/useEngine.ts`, `useHomeRail`, and the phase counts of `site/src/pages/Home.tsx`) `src/lib/card.ts` (`FixtureCard` in `site/src/components/app/fixture-card.tsx` and `playState` in `site/src/lib/play-state.ts`: live / started / delayed / final, scores, status line; a started match has no LIVE badge and says the source has no score), `src/lib/hot.ts` (`useHotRows` in `site/src/components/app/hot-props.tsx`: the scoring loop around the engine; `useTick` / `StandingMark` in `src/ui/tick.tsx`) `src/lib/fancy.ts` (`useFancyCards` in `site/src/hooks/useFancyCards.ts`) and `src/lib/player.ts` (`PlayerScreen`, `nextMatch` and the chart numbers in `site/src/pages/player.tsx`; `deriveChart` is pure and tested).

## Data path
The app reads the same files as the site: `/data/*.json` and `/api/live`, through the data gate.
* `GET /api/gate` returns the cookie and the unwrap key (`X-Cd-K`). The app sends the cookie header by hand (no browser cookie jar) and refreshes it on a 403 (`mobile/src/lib/net.ts`).
* Every request carries its own user agent (`FancyCash/<version> (<os>)`). Android's default one (`okhttp`) is on the gate's block list and is refused everywhere. The gate today lets in any client that is not on that list and sends no `Sec-Fetch-Site`; that is a speed bump, not a lock, so a key kept in the app would not be one either. If the gate is tightened, give the app its own explicit way in rather than a browser-looking user agent.
* The small files (fixtures, photos, identity) and `/api/live` arrive wrapped (`engine/wrap.js`: SHA-256 keystream). The unwrap needs `TextDecoder` and `crypto.subtle.digest`, which Hermes lacks; `src/lib/polyfills.ts` supplies both (SHA-256 from `@noble/hashes`, MIT, synchronous, because the unwrap hashes one small block per 32 bytes and a native call each would be thousands per poll). It is installed first, from `mobile/index.js`. The digest hands the main thread back after 8 ms of work (`FRAME_MS`), so a big file does not hold the screen.
* The site URL is `EXPO_PUBLIC_SITE_URL` in `mobile/.env.local` (ignored). It ends up in the built app, never in a tracked file. Player/team image CDN is `EXPO_PUBLIC_IMG_CDN` (same value as the site's `VITE_IMG_CDN`); without it `photos.js` builds empty CDN URLs and faces/crests 404 on device.
* The stats engine's data (`src/lib/data.ts`): `meta.json`, `index.json` and `matches.json` (about 4.5 MB) load once, then a player's own file (`p/NN.json`, 0.5 MB) when a row needs it. Hot props scores one day's priced lines against those files (`src/lib/hot.ts`, `use-hot.ts`).
* Team crests are the source's logos from `photos.json` (`teamLogos`), else the national flag (`flagUrl` / `flagCode`: U19/A/Champions share the senior flag), else initials, as on the site. No source AD jersey or stock helmet face.

## Look
The Home tab follows the site's phone Home: the brand header, 80%-width snapping fixture cards (state and format, crests, scores or start time, status line, series, Props — Test stumps use `sessionBadge` / `nextTestDayLine` from the engine via `cardModel`, same as the site), the In play / Pre-match / Completed phase strip (docked in the page flow, flush above the tab bar — not a floating pill; no series chips on the rail), and the six tabs (Fixtures, Player props, Fancy, Leagues, Saved, Contact). Colours come from the shared tokens; type is the site's pairing: Satoshi for text and titles, Barlow Condensed for 11 pt caps labels and all numbers (`font`, `cap`, `num` in `src/ui/tokens.ts`), loaded in `app/_layout.tsx` with the splash held until they are in. Below the rail: the market tape ("High odds hits" / "Low odds misses") and **Props**, fixture hashtags (`MatchChips`: overlapping bare crests in one ring + `ABR v ABR`, matching the site's MatchChip / AvatarGroup) then a mixed player+fancy list for the chosen match (`mixHomeRows` in `site/src/lib/hot-lines.ts`: rank by `hotOrder` first, rebalance only outside a ~⅓–⅔ band; today+tomorrow player lines scored so a tomorrow chip is not fancy-only; Player props and Fancy links in the header). Empty lists use the same `EmptyState` pattern as the site (title + body on a tonal surface). Prop rows and fancy Overview rows share the same chrome (condensed line, books, model edge without a pill box, MiniBars). The Player props tab lists the day's rows with the same prop row, a day chip row (Today, Tomorrow, then dates) and pull to refresh on both platforms (`RefreshControl`). Crests and player kit images use Expo Image `memory-disk` cache. Motion: pulsing LIVE dot, cards and rows rise and fade in (fewer staggered rows on Android to hold 60 fps), pulsing placeholders while lines are scored, price and so-far flashes with an arrow when they move. Horizontal hashtag scroll: iOS `decelerationRate=fast`, Android `removeClippedSubviews` + no overscroll glow. Native components wherever there is one: the system tab bar, `Segmented` (SwiftUI picker on iOS, Compose segmented buttons on Android: Over / Under, format, innings, In play / Pre-match / Resulted, Lines / Game log / Splits), and system form sheets for the info popovers (`app/info/[topic].tsx`, topics in `lib/info.ts`). Page headers and the filter bars are `BlurBar`s over the scroll view (a `BlurTargetView`); the sub-bars (format, innings) collapse as you scroll down (`useCollapseOnScroll`). Filters, alt lines and splits are accordions (`ui/accordion.tsx`, height and chevron animated on the UI thread). Loaders (`Working`) are centred in their section or page. The tab icons are the site's Ionicons, drawn as images (`assets/tab-icons`, made from the `ionicons` package). To compare with the site, run the browser preview (below) next to the live page at 375 px: the counts and the first chips are the same.

## Pages
The root is a stack with the tab group on the bottom (`src/app/_layout.tsx`, `(tabs)/_layout.tsx`); a page one level down is pushed over the tabs and has the reference app's header (`ui/page-header.tsx`: a round back button, the name and what it is centred, round Save / Share buttons at the right) and the system swipe-back. Taps (`src/lib/nav.ts`): a fixture card opens `/fixture/<id>`; a prop row or a market-tape row opens `/player/<index>?stat=&line=&fmt=&scope=` (the site's own parameters, plus `team`); "See all" opens the Player props tab.
* **Fixture page** (`app/fixture/[id]/index.tsx`): the match in a container (`ui/match-header.tsx`) and the site's four sections as a native segmented control: **Props**, **Match Fancy**, **Grid**, **Custom line** (was Trends). Props and Match Fancy only show when the books price them. A first-class match says it has no player props. Share sends the match text and link.
* **Match Fancy** (`ui/match-fancy.tsx`): scope chips (Match / each side) beside a Filters button (`L{n}`, default L10 like the site) that opens a sheet for the hit-rate window and Teams' form / At ground — same pattern as Props. Match-scope L10 is the newest 10 among either side's last 10 (`fancySample`); switching Match / NZ / IND keeps the peer market (`peerFancyFm`, e.g. Fours stays Fours) and the O/U line when still priced. "Bookmaker lines" ranked by edge; tapping a row opens `/fixture/<id>/fancy?fm=&sc=` (`app/fixture/[id]/fancy.tsx`), a dedicated market page with the median, chart, over/under, ground note and line ladder (like a player page). Match-level rows use a chart icon; team rows keep the crest. Ground note on each row is `N/M under at Eden Park` (`shortVenue`). Old `?tab=fancy&fm=` links redirect to the market page.
* **Grid / Custom line** (`ui/grid-table.tsx`): stat chips beside Filters (`L{n}`); the custom line, games window and (on Custom line) the minimum hit rate sit in the sheet. Grid team switch is chips. Grid: players down, last fixtures across, tinted by distance from the line. Custom line: players who clear the line often enough.
* **The live match** (`ui/match-header.tsx` + `ui/live-board.tsx`): scoreboard matches the site (series · mirrored crest/score · centre `StatusLabel` LIVE pill white-on-miss · live strip: bowler O-R-W + ongoing over balls via `formatBall` | batters with strike dot — no faces / partnership / CRR on the strip). Fixture scoreboard sits in an edge-to-edge `scoreShell` (`color.card` + bottom hairline) — twin of web `-mx-gutter bg-card border-b`; strip wash and accordion trigger borders share that full-bleed plane, content stays guttered. **Full scorecard** uses MarketTape-style segmented `Team · score` tabs and edge-bleed batting/bowling tables. Status marks (`LiveBadge` / FixtureCard / MatchStatus) share `ui/status-label.tsx`. Under a non-live match: same flush shell around `MatchHeader bare`; **Scorecard** accordion only below (Recent form is not stacked under the header — same as web, where Form is its own tab). Archive fallback unchanged (`lib/archive.ts`, `EXPO_PUBLIC_ARCHIVE_URL`).
* **In-play lines** (`lib/use-lines-live.ts`, `lib/merge-live.ts`): the books file with the started matches' live lines folded in by the engine's `liveMerge`, the same merge as the site's `useLinesLive`; `/api/inplay` (`inplayQuery`) is polled every ~15 s only while a priced match is on. Props, Match Fancy, the Fancy tab and the fixture page read it instead of the plain file, so a row whose line is a live price gets the red **Live** mark, "was N" (where the line opened), the progress bar (`ui/live-bits.tsx`, geometry in `lib/live-track.ts`) and the "From here" counts (`ui/live-spot.tsx`: batter's own history, similar in-play lines, similar team innings). Live markets that are not a batter's runs or a side's total are prices-only rows at the end of Match Fancy (`ui/live-market-row.tsx`). Rows are scored again when the live lines change (`live_sig` is in the cache keys). **Home Props order vs the site:** same `mixHomeRows` / `hotOrder`, but Android Home deliberately skips day-scope live-line history scoring (`use-hot.ts` `androidDay`) and never turns Fancy on for the Home mix (`use-hot-home.ts`) so cold start stays light — that is why the Home props mix can differ from web/iOS while a match is live.
* **Synced with the site (2026-11-15):** Fixture scoreboard / live strip / StatusLabel / full scorecard categories match web (see DESIGN_SYSTEM_CHANGELOG). Fancy `innScope` (CMM / 1st INN) sits on the meta line beside odds like props (`fancy-row`), not in the title. Earlier (2026-11-12): Test props and fancy tags (`scopeTag`, `innTag`, `BAT_FIRST_TAG`); live fixture opens on one `ScorecardCard`; Scorecard accordion only when not live; live-priced rows beside pre-match (`isLive`); Home rail from `config/home_rail.json`. Loading placeholders page-shaped (`ui/skeletons.tsx`).
* **Fancy tab** (`app/(tabs)/fancy.tsx`, `lib/fancy.ts`): every priced match not yet over with its best-edge markets (the book's line, the edge, the last ten results as bars), in the Home rail's order. Day chips + `MatchChips` filter like Player props. Cards use the FixtureCard / web Fancy panel shell (`color.card`, `radius.card`, gutter + stack gap) with zoned header (`surface-raised`) · rows · footer (`surface`); match chrome via `cardModel` + `LiveScore`. Tapping a market opens `/fixture/<id>/fancy`; the card header opens Match Fancy. Matches are scored one at a time with the main thread given back in between.
* **Leagues tab and competitions** (`app/(tabs)/leagues.tsx`, `app/competitions.tsx`, `app/league/[id].tsx`, `ui/tournament-stats.tsx`, `lib/league.ts`): the league chips (live and soon first, Big Bash on top), then the season picker, the season in four numbers, the leaders rail, Batting / Bowling / Overall lists (best five, "Show all") and the season-by-season bars. "More" opens the competition (Stats, Markets, Teams, Results); "All competitions" lists every one with eight matches or more.
* **Team page** (`app/team/[idx].tsx`): format, then Player grid (stat, line and games), Markets (the engine's match markets over the team's matches, a ladder for each) and Top batter (the team batting first); the star saves the team.
* **Saved tab** (`app/(tabs)/saved.tsx`): free sign-in (Google or email via Supabase Auth, same tables as the site). Watchlist / players / teams sync server-side; recently viewed stays on device. Set `EXPO_PUBLIC_SUPABASE_URL` and `EXPO_PUBLIC_SUPABASE_ANON_KEY` in `mobile/.env.local` (never commit). Add redirect `fancycash://auth/callback` in Supabase Auth URL config for Google. **Search** (`app/search.tsx`, the button in the header): players (typo tolerant), teams, matches and leagues; empty, it offers the tabs and the last players opened.
* **Player page** (`app/player/[idx].tsx`, logic in `lib/player.ts`), Match Fancy / web Player shape: sticky stat capsules + format / innings (those two tuck on scroll); sticky `PageHeader` title fades in as the hero name scrolls away. Identity hero (name, crest/side, profile, portrait; kit via `matchSide` / `?line=` / `?start=`). Metrics strip only on phone (no gauge — web hides it below `sm`). Chart first; centred O/U segmented + `LineStepper` + prop star (+ “main N” chip when off the book main); quiet `WindowPills` hairline band (no filter button beside). Hairline O/U hit-rate meters + book lanes (`SideBook` + `BookTable` twins); next-match card; Filters accordion (opp/ground quick picks first). Bottom tabs: Lines | Game log | Splits | When it hits (corr is its own tab; Alt lines / At a glance removed — ladder owns booked lines). Tables fit the width (`DataTable` / `Pill`); games from the engine once per stat and format.

```bash
cd mobile && npm ci
printf 'EXPO_PUBLIC_SITE_URL=%s\n' "$SITE_URL" > .env.local     # the site's address, from site/.env.local
npm run typecheck && npm test
npm run web              # browser preview on :8082 (react-native-web); Metro proxies the site (dev-proxy.js), no gate or cookie needed in the browser

npx expo run:android      # JDK 17 (JAVA_HOME) and the Android SDK (ANDROID_HOME) with an emulator or phone
```

## Performance
Stay on Expo/RN; speed comes from less JS work and virtualized lists, not a native rewrite.

### Start-up (2026-11-05)
Measured with `EXPO_PUBLIC_PERF=1` (see "Measuring start-up" below). Where the time went on the iOS simulator, debug build, before this pass: the schedule and lines were behind a wait for every other tab to mount; `matches.json` (about 9 MB) was over the body cache's 6 MB cap, so every launch downloaded it again (`r.text()` alone held the JS thread for 1.5 s); each of the ~16 player files cost a conditional request even when nothing had changed; the scored rows were thrown away between launches, so every launch scored ~280 lines again (6 to 8 s of JS, a third of it deliberate sleeping); and the live poll rebuilt the rail three times over.
* **Scored rows kept on the device** (`lib/hot-cache.ts`, wired in `lib/use-hot.ts`): a day's rows are saved when a pass finishes. A snapshot from the books file's current generation is the answer (nothing is scored); an older one (under 3 hours) paints at once and is replaced when the fresh pass lands.
* **Stats files pinned to the data build** (`lib/net.ts`, `lib/body-cache.ts`, `lib/data.ts`): `meta.json` (always asked for, 358 bytes) says which build is current; index, matches, identity, names and the player files kept under that same build are read from the device with no request. A new build revalidates them as before (304 or a new body). The body cache cap is 24 MB, so `matches.json` is kept too.
* **Home paints from the last launch's schedule and lines** (`lib/queries.ts`: `initialData` peek for fixtures + lines + kept live when under 3 hours old; counted stale so the real one is asked for at once). Prefetch starts in `_layout` once fonts are ready. On Android, `useLive({ defer })` delays only the **/api/live network** poll (~4 s); kept live still paints scores. A failed `/api/live` or `/api/inplay` poll soft-fails (kept body / `null`) so the rail does not blank. **`useLinesLive` never starts the stats store** — only Fancy / Leagues / Saved / Player / Fixture do via `useStore`; in-play merge runs only when `matchesReady` (no second Android merge delay on top of live defer). Store boot matches the site: `createStore({ deferMatches: true })`; **every surface that reads `store.M`** waits for `matchesReady` — Player chrome still paints from the index alone. Live-spot / live-board only *peek* the store cache (enabled:false). Android unwrap prefers a worklet runtime and falls back to the yielding JS path. **Home layout:** horizontal fixture rail is a sibling of the props `ScrollView`, height from the first card’s `onLayout` (not a width×0.72 guess).
* **Tabs mount when first chosen** (`ui/lazy-tab.tsx`): the native tab bar mounted all six at launch, so Props, Fancy, Leagues, Saved and Contact rendered and started their own queries while Home was loading.
* **Scoring** (`lib/hot.ts`): matches already on are scored first (`lib/hot-priority.ts`), the first row is published at once (then every 600 ms on iOS / 1000 ms on Android), the loop sleeps 4 ms per 8 ms of work on iOS and 12 ms per 6 ms on Android (lighter Android duty cycle so scroll stays alive during load), and the lines are grouped by match once instead of filtered for every line. Home’s Props block uses `useHotHome` (day-1 scoring deferred until today has rows; Fancy delayed on iOS, off on Android Home cold start) and mounts via `useLater`.
* **Cheaper live poll**: the rail is built **once** per input change and shared by Home, Props and Fancy (`use-rail.ts`: module-level `sanitizeRail` / `homeTeam` identities; engine `teamKey` memoized). A quiet poll that decodes to the same text keeps object identity (`net.ts`) so the rail does not rebuild. Hidden tabs are frozen (Suspense; Expo Router 58 ignores `freezeOnBlur`), so Home does not re-render on a live poll while Fancy is in front. In-play merge is sliced (`mergeLiveLinesSliced`); Fancy cards publish at most every 400 ms. The Resolver builds in slices behind a Proxy (`data.ts` / `Resolver.create`) so Fancy open is not a half-second block. Tab first-open and Home props / player / fixture bodies use `lazyTab` / `useLater` (`startTransition`).
* **Back-navigation / cache (2026-11-14):** Hot history scoring is keyed by the books file generation only — not `live_sig` — so a 15 s in-play poll does not rebuild Home/Props (`use-hot.ts`: base query + small live-only follow-up + `patchHotQuotes`). Fancy cards match the site (standing overlaid; no live_sig in the score key). Shared feeds keep `gcTime` of 1 hour (`FEED_GC_MS`). Fixture → fancy/ground uses a nested stack (`fixture/[id]/_layout.tsx`) so the match page stays mounted. Loading gates use cached data and do not blank on background refetch.
* The splash holds for at least 1.1 s (was 1.6 s): the drawing finishes in about a second.
* **Published hot rows (2026-11-12, PROJECT_GUIDE 5.11):** the builder step `site/scripts/hot-rows.mjs` writes the history of every priced line to `/data/hot-rows.json`; `lib/queries.ts` `hotRowsQuery` reads it when its `build` equals `meta.json`'s, and `scoreHotRows` (`lib/hot.ts`) turns every covered line into a row at once (`seedRow`, the prices are the phone's own books) and scores only the rest, asking for the store and the player files (`loadStore`) only then. Done on the server: the scoring. Not done: splitting the innings table (`inn`, over half of `matches.json`) out of the file the engine loads first.
* Earlier passes: Props and Fancy use FlashList; unwrap yields every 8 ms; body cache + ETag 304; polling follows app focus (`watchAppState`); wrapped responses whose ciphertext matches the kept fingerprint skip unwrap and unchanged bodies reuse the same object, so a poll with no change re-renders nothing (`lib/net.ts`, `lib/body-cache.ts`).

### Measuring start-up
Judge feel on a **release build on a physical phone**. Debug builds, Expo Go, the iOS Simulator and especially the Android emulator (software-rendered) are several times slower and are not a speed verdict.

```bash
# Debug (dev loop only — not for "is it fast?"):
cd mobile && EXPO_PUBLIC_PERF=1 npx expo start --port 8081
xcrun simctl terminate booted cash.fancy.app && xcrun simctl launch booted cash.fancy.app

# Release on a real device (the bar):
cd mobile && EXPO_PUBLIC_PERF=1 npx expo run:ios --configuration Release
# or: EXPO_PUBLIC_PERF=1 npx expo run:android --variant release
```
Cold start: clear the app's MMKV (`Documents/mmkv` on iOS; app storage on Android) before launch. Warm: leave storage intact. `lib/perf.ts` prints `[perf] <mark> <ms since the bundle started>` (fonts-ready, rail-ready, first-fixture-card, first-props, scoring-done, fancy-ready, splash-done, store-ready), `[perf-span]` for each network read (net / body / unwrap / parse) and any slice of work over 15 ms, `[perf-render]` for React commits over 12 ms, and `[perf-stall]` / `[perf-jank]` for stretches where the JS thread did not answer a 100 ms timer. The same lines are kept in storage (`perf-log`) so a release build (no readable console) can still be read back from the device. Nothing runs without the flag.

Live-poll hitch check: with PERF on, watch `[perf-span]` for `/api/live` and `/api/inplay`. Unchanged ciphertext reuses the last parsed object (`lib/net.ts`) so a quiet poll does not rebuild the rail; a real score change still unwraps once.
