# Project guide: cricket-data + Cricket Props Hub

Everything a new contributor (human or AI agent in any IDE) needs to pick this project up. Start here, then follow the links.
Operations (secrets, runbooks) live in [OPERATIONS.md](OPERATIONS.md); the site's feature list in [SITE.md](SITE.md); the StatsHub comparison in [SITE_MAP.md](SITE_MAP.md).

## 1. What this is
Two products in one repo, both **100% free to run**:

1. **The dataset** (`src/cricket_data`, `data/`): 21k+ cricket matches since 2001 (men's and women's) from Base ball-by-ball, stored as monthly
   gzipped CSVs, plus **provisional** matches scraped from Source A to cover the days before Base publishes. A `cricket-data` CLI queries and maintains it.
   An hourly **value-bets** pipeline (`src/value_bets`) prices player props against free odds sources.
2. **The site** ("Cricket Props Hub", `site/`, `src/cricket_site`): a StatsHub-style player-props and stats website on Vercel Hobby. Hit rates over any line, DNP-aware form
   charts, fair decimal odds, partnerships, team/venue/competition markets, player trends, a Prop Hunter (value bets), live scores with player so-far vs booked lines
   (~15 s; the server settles each priced line, see 5.4c), and an ask-anything box (an LLM turns the question into a structured query; **all numbers come from the data**).

### Non-negotiable rules
* **Free only**: no paid services as hard dependencies. Optional keys (xAI Grok / Gemini for the chat parser) degrade gracefully to a built-in parser.
* **Decimal odds only** (never American/fractional). Player props and fancy markets only; no match-winner focus.
* **Props are never deleted.** Once a fixture has arrived and the books have priced it, its props stay: `value_bets/archive/` keeps every match's lines for good (and Feed H's full market catalogue: every open market of a fetched match, mapped or not) and the fixture page falls back to it (`docs/VALUE_BETS.md`, `docs/SITE.md`). The home list may stop showing a finished match; no job may delete or trim the archive.
* **The in-play log only grows and nothing reads it for a verdict.** `inplay_log` (5.10) holds every in-play line with its score state, for later statistical grading: no job or script updates or deletes a row (a database trigger refuses it too; retention is forever), and settlement, the archive and the site never read it.
* **Data rules live in the data, not only in client code.** Which match shows, for how long and what counts (the keep windows, when a finished Test goes) is decided in the pipeline, the builder or the database and published, because the mobile apps cannot be updated at will; the client only reads it. A rule that only the browser applies is a bug for an app in the wild.
* **Exchange rules**: T20/ODI summary markets void unless 80% of overs are bowled in both innings (Hundred 80/100 balls; T10 48/60; 60-over 288/360), **except that an innings which ended naturally is complete** (all out, or the chase reached its target in a match no DLS-style adjustment decided): the rule is for a match cut short by weather or the like, not for a quick chase or a bowled-out side. The match winner (and so bat-first win %) never depends on it; Tests void unless a result or 300 (5-day) / 200 (4-day) overs;
  30s = 30-49, 50s = 50-99, 100s = 100+; double-digit = 10+; single-digit = 1-9 (ducks excluded); team markets count only the team batting first; retired hurt is not a wicket;
  penalty runs count; super overs ignored; **a player named in the XI who never batted (bowled) has his batting (bowling) bets void**: the chart shows VOID (named in `xi`, no row) vs DNP (not in the XI), both excluded from hit rates.
* **Player performance (`points`)**: runs + 20 per wicket + 10 per catch + 25 per stumping, per match, from the ball by ball data (`parse.py` counts a catch for the fielder, a caught-and-bowled for the bowler, a stumping for the keeper; scraped matches use the totals' `catches` / `stumpings`). Live so-far uses the same formula (`liveStat` in `live.js`) off the scorecard how-out (2 = catch, 3 = caught-and-bowled to the bowler, 8 = stumping). A player named in the XI who did nothing is **0 points, not void**; one not named is DNP. A fielder who neither batted nor bowled has no player entry in the historical files, so his credits are not counted there; the live card still gives him a row so a catch or stumping is counted. No model prices it yet.
* **Never mix formats**: T20 = T20 + T20I, ODI = ODI + 50-over List A, Test = Tests only, **The Hundred / T10 / 60-over are their own formats**. A T20 in a Test series does not price the Test. First-class (`MDM`) is excluded.
* **Show freshness** where it helps (Ask answers, About / data notes): newest Base match date + whether provisional games are included. Not on the player page (the sample line under At a glance is enough).
* **Never print or commit secrets** (`scripts/check_public_safe.py` runs in CI and also bans hosted-service hostnames (Vercel, Supabase and Workers subdomains), absolute home paths and `.env*` files).
* **Software is source-available** (Functional Source License, [LICENSE](../LICENSE)); match files under `data/` stay CC BY-SA. A competing hosted props/fancy service is not a permitted purpose. Feeds and keys stay in GitHub secrets, not the tree.

## 3. Data layer (`src/cricket_data`, `data/`)
* **Canonical**: `data/matches/YYYY-MM.csv.gz`, `data/players/YYYY-MM.csv.gz` (one row per player per match). Columns in [DATA_DICTIONARY.md](DATA_DICTIONARY.md). Written deterministically
  (sorted rows, gzip mtime 0) so unchanged months produce no git diff.
* **Provisional**: `data/provisional/*.json`, one per scraped match (`crex-<slug>.json`). They carry player totals and, for matches scraped since the scorecard summary was kept, each innings' stated runs / wickets / balls (`innings`; extras = stated runs minus the batters', so scores, extras and all-out are exact). Every saved match lacking it, of any format or league and the permanent classes too (provisional first, newest first), gets it from `cricket-data refresh-innings`, which the scraper workflow runs for a few matches per run (it adds only the `innings` key, checks the card against the saved player rows, and gives up on a dead page after three tries in `data/state/innings_refresh.json`). A failed re-scrape never empties a stored scorecard. No ball-by-ball. A provisional match is deleted once Base
  publishes the same fixture (same teams, +/-1 day) and is logged in `data/reconcile_log.csv`. Permanent classes (`cricsheet_missing`, `cricsheet_withheld`) are kept. See
  [PROVISIONAL.md](PROVISIONAL.md), [PERMANENT_MATCHES.md](PERMANENT_MATCHES.md).
* **Player ids**: `cricket-data link-players` fills Base registry ids ("Harry Brook" -> `4ae1755b`, "Chamari Athapaththu" -> `ac56b5a7`) into provisional files using `data/mappings/player_aliases.csv`; unmatched names land in
  `data/provisional_unmatched.csv`. A side Base has no roster for at all (Afghanistan, many associates) gets the Base id of the one player with exactly that full name on any team, else a minted id
  (`registry.minted_id`: 8 hex of the full name and gender, stable across runs), so its matches build a history and the books' lines for its players can be matched; a Base id found later goes in `player_aliases.csv`.
* **Fixtures**: `cricket-data fixtures` reads Source A's home list and `/schedule` every scraper run. The schedule page is live and upcoming only, so a Test at stumps drops off it while home still shows it; both pages' `getFixture` rows are merged (home wins for the same match). Then the following schedule pages in headless Chromium (press "Next", read each page's cards, UTC; no venue) until it is 10 days ahead (`fetch_schedule_paged`); if the browser read fails it falls back to the first page plus home; it never overwrites the file with an empty result. A Test/FC the page then drops is kept 6 days (`Live` until there is a result). The older sitemap crawl (`--sitemap`) surfaced stale placeholder pages and is no longer the default.
* **Linking scraped players**: besides `link-players`, the site builder links still-unlinked scraped names through Source A's full-name list (e.g. Afghanistan, whose matches Base withholds): ~1.7k extra rows.
* **Source A scraper**: `crex_*.py`, `scrapers.py` (Playwright for pages, plain HTTP for the Source A sitemaps; see [SCRAPER.md](SCRAPER.md), [SCRAPING_REALITY.md](SCRAPING_REALITY.md), [SELF_HEALING.md](SELF_HEALING.md)).
* **Ball-by-ball**: `cricket-data crex-balls` scrapes Source A's commentary feed into `data/balls/` (verified against the scorecard before storing), see [BALL_BY_BALL.md](BALL_BY_BALL.md).
* **CLI**: `cricket-data update | backfill | health | fixtures | crex-balls | stats | query | link-players | freshness | export-sqlite`.
* **Freshness**: `cricket-data freshness --max-age-days 3` fails when the newest *canonical* match is old; the scraper's provisional matches still cover the gap on the site.

## 4. Value bets (`src/value_bets`)
Hourly pipeline: pulls free odds (Exchange S exchange API, an unofficial Book A mirror), prices player props with a negative-binomial model, writes small committed outputs to
`value_bets/out/` (`value_bets_latest.json`, `new_alerts.json`, `alerts_history.jsonl`). The site's Prop Hunter reads `value_bets_latest.json` live from GitHub raw and falls back to the
snapshot built into the site. Details: [VALUE_BETS.md](VALUE_BETS.md), [MODEL_BACKTEST.md](MODEL_BACKTEST.md). No free source prices cricket player props officially: that is why edges are rare.

## 5. The site

### 5.1 Build pipeline (`src/cricket_site`)
`python -m cricket_site.build --zip all_json.zip --data data --out site/public/data [--value-bets value_bets/out] [--people people.csv --photos] [--site-url URL]`

1. `parse.py` parses each Base ball-by-ball JSON into batting rows (position = order of first appearance at the crease; runs/balls/4s/6s; dismissal kind), bowling spells
   (wickets exclude run outs/retired; runs conceded = batter runs + wides + no-balls + penalty), partnerships (pair, wicket no., runs, balls, who was out), and per-innings market
   aggregates (fours, sixes, 30s, 50s, 100s, 10+, single-digits, ducks, highest over, most conceded, most wickets, extras, run-outs, top score, top-scorer ids) and the over tape (cumulative runs after each completed over). Super overs ignored. `qualifies()` implements the void rules.
2. `build.py` merges provisional matches (deduped against the zip), infers hosts (home/away), assigns integer ids, shards player data into 64 files and writes JSON. A scraped batting/bowling/fielding row that names no side is skipped (empty team used to `KeyError` and sink the Vercel data build).
3. `crex_assets.py` matches Source A sitemap names to Base players (conservative: surname + first initial; ambiguous names skipped) and teams (with a small alias table).
4. `identity.py` builds the player-identity table from the photo map, the books' names and a hand-checked file (see 5.7); its links also feed the photo map and the scraped-name linker.
5. `assets_sync.py` copies images into our own Supabase Storage (see 5.6).

Output files in `site/public/data/` (all JSON, columnar = one array per field; **generated, gitignored**):

### 5.2 Engine (`site/packages/engine`, dependency-free ES modules; runs in browser and node)
`identity.js` (lookups over the identity table: our id <-> the live source's id, the books' names) · `store.js` (load + join rows to matches; home/away; shards) · `filters.js` · `stats.js` (hit rate, Wilson interval, fair odds; pushes void) · `lines.js` (book lines; two stamps of one fixture within the 14 h / 6-day window are one match) · `props.js` (player report, DNP-aware form chart over team
fixtures, correlated props) · `markets.js` (match/team markets, top batter) · `tournament.js` (editions of a league or series, and the leaderboards and season-by-season measures of the Stats tab; SITE.md "Tournament stats") · `partnership.js` · `resolve.js` (typo-tolerant player/team/venue/competition resolution) · `plan.js` (query plans: sanitize,
resolve, run) · `nl.js` (rule-based question parser, the LLM fallback) · `prompt.js` (LLM instruction) · `live.js` (Source A snapshot parse, name match, so-far vs line, `settleLines`: the server's per-line results) · `rules.js`, `util.js`.
**Invariant: every number shown comes from the engine; the LLM only emits a validated plan** (`sanitizePlan` whitelists fields; see `site/tests/nlp.test.mjs`).

### 5.4 Ask-anything API (`site/api/ask.js`)
`POST /api/ask {question}` -> `{plan, model}`. Provider: **xAI Grok** if `XAI_API_KEY` (model `XAI_MODEL`, e.g. `grok-4.20-0309-non-reasoning`), else **Gemini** if `GEMINI_API_KEY`; none -> 503 and the client uses `nl.js`.
Per-IP rate limit + daily cap, key only in headers, reply passed through `sanitizePlan`. The browser resolves names and runs the plan locally.

### 5.4b Live scores (`site/api/live.js`)
`GET /api/live` -> `{asOf, source: "live", matches}` (wrapped with `DATA_WRAP_KEY` when set, same XOR-SHA256 as the small `/data` files; the browser unwraps after `/api/gate`), built from Source A HTML pages (robots Allow; never the source's API endpoints) and intersected with `book_lines.json` (player props, event markets, or fancy). Matches with no odds are dropped. The **home** list still shows a Test at stumps after the **schedule** page (live and upcoming only, cached ~5 min by Source A) has dropped it; both are parsed and merged (`mergeSchedule`) for the match list, URLs, format, start and a first score. The response waits for every live match's pages and includes a finished or upcoming card only when it arrives within a short budget, so one slow finished card does not hold the list (the match-state writer still reads every card). For live matches and priced ones about to start, the **match** page (`getSV3`, `max-age` 10 s) gives the fresh score, the current pair with strike, the bowler, partnership, CRR/RRR and the last deliveries, and `/match-scorecard` (`getSC4`) gives every innings: batting how-out / R / B / 4s / 6s / SR, extras, FOW, yet-to-bat, bowling O / M / R / W / Econ. A Test at close of play drops off that schedule page (status 2, no result): `/api/live` still reads it from home, then our schedule file, for the rest of the 6-day window, keeps it `live` even if that match page fails, never skips its page fetch in favour of finished games, and the card shows the scores plus the session badge ("Stumps", "Lunch", "Rain delay", "Paused") and the session line ("Stumps - Day 3", or "Close of play" when the source has none). Source B is not used: its summary cards trailed its own header by an innings. `crexMatch` merges the pages (match-page scores beat the schedule's; a page that failed just leaves its fields empty), and `liveBoard` only ever shows the batting side's not-out pair, so a finished innings can't pose as the current one. The fixture header renders that snapshot as a live board plus the accordion. A match with no row in it and no `Live` from the schedule is never shown as live: the header and the rail card say "Started" with "Score not available from our source" (`playState` in `site/src/lib/play-state.ts`, one decision for both). No key. Cached ~15 s (`s-maxage` + in-memory single-flight). The Vite dev server mounts the same handler. Team names are matched to Source A fixtures; players are matched to booked lines **by id through the identity table** (5.7), with names (`HC Brook` ~ `Harry Brook`) only as the fallback for a player the table does not know. Kick-off and countdowns stay in the viewer's time zone. Each match also carries `lines`, see 5.4c. Unofficial and can change.

### 5.4c Settled lines and stored results
A priced line's "so far / final / Cleared / Missed / Push / Not in XI" is worked out **on the server**, so a matching or settlement fix is one server change and no browser holds a rule of its own.
* **`/api/live` -> `matches[].lines`.** For every match it read, `settleLines` (`site/packages/engine/live.js`) takes each player line the book file has for that match (same two sides, start within 14 h, or 6 days for a Test) and reads it off the card (a Test's first- or second-innings line, `inn` 1 or 2, off the card's innings of the player's own side, not the match total; it is `final` once a later card innings has actually begun — batters or totals, not an XI-only stub the source pre-lists — or the side is all out, or the match is over, and the entry carries `inn`): `{pid, stat, line, value, state: "live" | "out" | "final", verdict: "cleared" | "missed" | "push" | null}`, with `liveState` and `lineVerdict` giving state and verdict (an over line is cleared the moment the count passes it; a miss or push only once it cannot move). The player is found by id through the identity table (5.7), names only as the fallback. A player the named XI rules out is `{value: null, notInXI: true}`; a player with no row (he may not have batted: VOID) has no entry. The function reads the table from `public/data/identity.json`, shipped with it (`vercel.json` `includeFiles`; else `IDENTITY_URL`, else the production domain's copy) and says how many ids it holds as `linked` in the body. Without a table names decide, as before.
* **Player-performance so-far** is that same scoring: `liveStat` for `points` is runs + 20×wickets + 10×catches + 25×stumpings. Catches and stumpings are read from the scorecard how-out (2 / 3 / 8), a missing credit is 0 so far, and an all-rounder's bat and bowl rows are merged even when one row carries the source id and the other used the printed name as id. A fielder who has not yet batted or bowled still gets a live row, so a catch or a stumping is not dropped.
* **The browser** (`lineStanding` / `lineNotIn`, used by `hot-props.tsx`) shows, in order: the server's entry; the result stored in the match's archive file; its own reading of the card (kept for a body from before `lines` existed and for a player the server could not place); the player's game as the data records it.
* **Fancy so-far.** Fancy markets are not player lines, so `settleLines` does not cover them. `fancyStanding` (`live.js`) reads the innings totals (`liveMarket`) and `lineVerdict` against the booked line, with `fancyState` saying whether that so-far can still move (a side's own 1st/2nd innings is final once that turn is over; a limited-overs team total is final with that innings; a Test match total and a whole-match market stay live until the match ends). A fancy side run line tagged `bat_first` (first N overs, or the full innings) voids once that side is bowling first; premium fours / sixes are not tagged and stay live for both. Match Fancy scores a `bat_first` market only on matches where that side batted first. Overlay is at view time from the 15 s poll; the scored history is not rebuilt every 15 s. Same words as a player prop (`StandingMark` / `Tick`).
* **Stored results.** Once a match is final, `python -m value_bets.archive --results <site>/api/live` (a step of `value-bets.yml`, hourly; needs the repository variable `SITE_URL`) reads that body twice, a minute apart, and adds `results: [{pid, stat, value}]` (with `inn` for an innings line) to the match's archive file (`value_bets/archive/YYYY-MM/<fixture id>.json`): only `state: "final"` lines of a `status: "final"` match (an innings line is also stored once it is `final` in a match still being played), only (player, stat, innings) triples the archive priced, only values both reads agree on. A pair already stored is never changed (a pair that was missing is added later); nothing is removed, and the hourly archive pull carries `results` along. `withArchive` puts each result on its archived line, so a fixture page for an old match shows how every line went with no live feed and no name matching. A match whose lines were not read (a match the source never listed) has no results; a wrong stored value is fixed by hand in that file.
* A multi-day match is final only when its own page says so (a "Completed" in our schedule file without a result line is a guess).

### 5.5 Photos, flags, logos
Team logos / player photos come from Source A's public sitemaps + image CDN (`$IMG_CDN_BASE`), fallbacks: Wikimedia Commons (Wikidata P2697->P18), flagcdn flags, initials/silhouette.
The browser tries **our own copy first** (5.6). Images belong to their owners: check terms before commercial use.

**Why a player shows the silhouette** (measured 2026-11-09 on the 216 priced players, then the whole player table; each has one fix at the source, none a special case):
1. *The source's stock avatar passed for a photo.* The source serves one of three stock helmet-and-head pictures under every player id it has no photo for, and the sync stored them like faces: 3151 of 6851 stored pictures, 1711 of the 4855 linked players. Found by content (`assets_sync.placeholder_ids`: one stored hash shared by 20+ players), such a player gets no `c:` photo in `photos.json` (`build.faces`), the Commons photo when Wikidata has one, else our silhouette. His identity link (live scores) is untouched.
2. *The source's player list drifted.* It loses players from day to day while their pages and images stay up; 1539 players had a photo link in an earlier build (the images are in our store) and none now. `crex_players` remembers every id and name any build saw: `assets_sync.remembered_players` feeds them back (`crex_assets.merge_remembered`). Matching runs on today's list first, exactly as before, so a remembered name can only add a link, never make a working one ambiguous.
3. *Players only the scraped matches know.* A side Base has no roster for gets a minted id and no Base name (824 players, `names.get(pid)` empty), and the photo matcher only looked at Base players. `build.provisional_people` hands them over with the full name the scorecard prints and they are matched by it.
4. *One person, two ids.* A minted id next to the Base id that has his initials-and-surname name ("Dewan Marais" / "D Marais"), or two Base ids for one player ("CBRLS Kumara"): the source has one page. The second id shares the face (`identity.build` returns it as `also`, never in the identity table, where a source id stays one id's), by rule for a priced minted id and by hand for the rest (5.7).
5. *The name cannot be matched:* the Base name starts with the initial of an earlier given name ("CBRLS Kumara" is Lahiru Kumara), the source spells him differently ("Prasiddha"), or two source players share the name ("Usman Khan" x3). A hand-checked line in `data/mappings/player_identity.csv`; the Site run summary lists them.
6. *The source has no page for him* (a new Nepal U19 player): the silhouette is right.
`meta.json` carries `priced_players`, `priced_with_photo` and `photo_shared`, and the Site run summary prints the faces line.

### 5.7 Player identity table (`src/cricket_site/identity.py`, `site/packages/engine/identity.js`)
The data knows a player by our id and a history name ("V Suryavanshi"), the live source by its own id and full name ("Vaibhav Sooryavanshi"), the books by whatever they print ("Kusal Mendis" for "BKG Mendis"). Matching those by name fails differently in every place, so the site build links them once, by id, into `identity.json` (`s`: our id -> the live source's player id; `b`: our id -> the names the books use when they differ from ours). The browser loads it with the other data files, and the live lookups (`livePlayer`, `notInXI` via `hot-props.tsx`) find a player's row by the source id first; names are the fallback for a player the table does not know, and a row that belongs to a different linked player is never taken for him.
A source id comes from, in order (an id is never given to two players): 1. `data/mappings/player_identity.csv` (`player_id,source_id,note`: a link somebody checked by hand, overrides everything); 2. the photo map's conservative name match (two equal-strength source namesakes leave a silhouette); 3. the books: a *priced* player (the pipeline already resolved a book line to his id) whose history name or book name equals exactly one source full name that nobody else holds — or, when several source players share that name, keeps a photo link that is already one of them and otherwise drops a namesake and reviews. The links also feed the photo map (a linked player gets his source photo), the source-id index for `assets_sync`, and the scraped-name linker.
**One person under two ids** is a photo-only link (`also`, 5.5): the identity table keeps one id per source player, but a second id of the same person shares his face. Automatic for a priced player with no Base name whose exact full name picks one source player that a name-compatible Base player (surname and first initial, `match_players`' own rule) holds by name match (never one a hand line gave); by hand for the rest: repeat the source id in `player_identity.csv`, the first line holds the identity link and later lines only the face (CBRLS Kumara next to a second Kumara id). The same holds when both ids are priced and both books-exact-name claim the page: the Base-named one whose name fits holds the link and the minted ones share the face (two Base-named claimants stay namesakes: neither). The name our own data uses first (`hist`) decides when it picks exactly one source player, so a book that prints another spelling under his id ("Avishka Fernando" under AM Fernando) does not turn one page into "several". A minted id's photo-map link waits behind the Base players and the books, so it can never take a page one of them would have.  The reasoning: the source's page is the ground truth of who is one person, and our minted ids over-split.
**Review list.** Every priced player that could not be linked is written to `identity_review.json` with the reason and the source players he might be (`suggest`: same or near surname, given name starting with one of his initials; never linked automatically). The Site workflow prints it in the run summary; fix a row by adding its line to the CSV. The pipeline (`value_bets/names.py`) does not read the table yet, and the fetchers stay separate (one outage must not stop the others).
Backfilling: `python -m value_bets.archive --backfill-book-names` adds `book_name` to archived lines filed before the field existed, where the archive knows exactly one spelling for the player (it only ever adds a field).

### 5.9 Player profiles (`src/cricket_site/profiles.py`)
Role, batting hand and bowling style exist in neither Base nor its people register (identifiers only), so they come from the source's player page (`/player/<name>-<source id>`, robots-allowed, HTML only; the "Role", "Bats" and "Bowls" rows). `python -m cricket_site.profiles` runs in the Site workflow after the data build (never on a pull request; `continue-on-error`): it takes the linked players from `identity.json`, priced ones first and then by matches played, fetches at most `--limit` pages (default 250, repository variable `PROFILES_LIMIT`) within `--budget` seconds at one request per `--pause` seconds through `PoliteFetcher`, and commits `data/profiles/profiles.csv` (`source_id,role,bat,bowl,checked`; keyed by the source id, so the file names no host). A player with any value is never fetched again; a page that gave nothing is asked again after 60 days. A source outage, a missing list or five failures in a row end the step with exit 0 and the files as they were, so neither the build nor the guard can fail on it. The text is reduced to the fixed vocabulary in `profiles.py` (`norm_role`, `norm_bat`, `norm_bowl`; a style the vocabulary does not cover stays empty). `build.py` writes `profiles.json` from the stored file on every build, so a player appears on the site one build after he is fetched.

### 5.8 Data guard (`src/cricket_site/guard.py`)
`python -m cricket_site.guard --site site/public/data --data data [--live <url or file>] [--summary <file>]` runs in `site.yml` right after the data build and before the deploy, on every build (hourly, pushes, PRs). It reads the built data (`fixtures.json`, `matches.json`, `lines.json`, `identity_review.json`), the dataset (`data/provisional`, `data/balls`) and optionally the live route's body, prints a table to the job summary and **exits 1 only for a hard check**, so the last good deploy stays up. Each rule is restated in plain terms, never by calling the builder's or the engine's own function (a check that did would agree with a bug in it); the one place the engine is run (c) is compared with a recount. The windows it uses (`KEEP_S`, `CARRY_S`) are pinned to `lines.js` and `booklines.py` by a test.

| | level | what it holds |
|---|---|---|
| a | hard | a fixture published `Live` has the schedule's word for it (`source: "src"`); a stop-gap row from the books can only be Upcoming, Started or Completed. Warn (`a-live`, needs `--live`, the workflow passes the site's `/api/live`): the live body lists a match in play with no score and no players |
| b | hard | a fixture flagged `Live` / `Started` is inside its keep window (24 h, a Test 6 days, an hour of grace) and has no result; the published book lines are no older than the pipeline's carry window (40 h, a Test 6 days) when the file was written. Warn (`b-fresh`): the book lines file is more than 3 h old. The static data cannot know when a Test ended, so "24 h after its result" is not checked here |
| c | hard | each edition's bat-first win % (`site/scripts/edition-bat-first.mjs` runs the engine's `editionSummary` on the built data) equals a plain recount over every match in it with a winner and a known first-innings side (the summary-market filter must not apply; WBBL 2026 read 3 of 6 for 3 of 7). Skipped without node |
| d | hard / warn | `d-complete` (hard): a limited-overs match whose innings both ran their course (first all out or its overs bowled; second also if it overtook the first and won) is not void for summary markets, unless the build flags it `dls`. `d-share` (warn): more than 20% of a format's matches void in one ISO week (at least 10 matches, last 8 weeks) |
| e | warn | a scraped match's stated innings total (`innings` in `data/provisional/*.json`) equals the batters' runs plus the ball-by-ball extras and the ball-by-ball total (`data/balls`); a stated total below the batters' runs. Tests and first-class are out of scope (four innings) |
| f | hard | one pair of sides (`SAME_SIDE` folded, same gender) is not two fixtures within 12 h |
| g | warn | priced players that could not be linked to the live source (the list `identity_review.json`; 5.7) |
| h | warn | `hot-rows.json` (5.11), when there is one, is for this build of the data (`build` = `meta.json` `built_at`), well formed, under 6 h old and kept at least half of its priced lines |

A hard failure prints the matches at fault in the summary (`::error` lines too). Fix the data or the rule that produced it, not the check; a check that is wrong is fixed in `guard.py` with a test. Add a new invariant as one `check_*` function, one row in `run`, and a test that feeds it deliberately wrong data (`tests/site/test_guard.py`).

### 5.10 In-play line log (`site/packages/engine/inplay-log.js`, `site/scripts/inplay-log.mjs`, table `inplay_log`)
**What.** An append-only Supabase table of every in-play line the price feed and the other books list while a match is on, kept for later statistical grading (how did an in-play line stand against the score when it was offered, and how did it settle). It is **data only**: settlement stays on the pre-match lines (`book_lines.json` and the archive, `settle` in `archive.py`, 5.4c), the site never reads it, and no job or script updates or deletes a row (a trigger on the table refuses it as well; retention is forever; dropping the trigger is a deliberate maintainer act). RLS is on with no policy: only the service key reads or writes.
**How.** The in-play snapshot job (`inplay.yml`, 5.4b / docs/OPERATIONS.md "Cadence") already reads the lines up to four times a minute. With the repository variable `INPLAY_LOG=1`, after each round `site/scripts/inplay-log.mjs` appends rows:
* **Only changes.** One line = (book, kind, market or subject, innings scope, line). A row is written when a line **first appears**, when **either price moves** (a pick: any outcome's price), and when a line **comes back** after a round in which its own book was listed without it (the main line often moves away and back). A repeated identical read writes nothing, and a book that drops out of a round (a failed feed read) and returns is not a storm of rows. Disappearing is not written. The previous value of every line is read back from the table (`inplay_log_latest`, once per run per pair of sides) and advanced as rows go in, so a new run (every minute) does not repeat what the last one wrote; if the read-back fails nothing is written for that match that round, and a failed insert is retried next round (idempotent: unique on match, line and time).
* **Every market the feed gives**, including the ones the site hides (`keepLiveOu`, `milestoneRows`: method of dismissal, single over, fall of wicket, milestones, picks). The site filters for display only; the log keeps all of it. Kinds: `player_runs`, `team_runs`, `ou`, `pick` (as `parseQuotes`), the book's published name, the market's name as listed, the line, over / under prices (or `outcomes` for a pick).
* **Score state on every row**, from the site's own `/api/live` (`SITE_URL`, the same ~15 s cached body the browsers read, unwrapped with `DATA_WRAP_KEY`: no second source, no new service): the batting side, the match's current innings, runs / wickets / overs (and the same in balls), the session badge, and a small `ctx` (display score, status, summary, run rates, partnership); for a batter line his own runs and balls so far in that innings. `inn` is the line's innings scope: a batter's own side's current innings (a Test: 1 or 2, read off the card: the batter's position among his side's innings, latest first, as the site's innings scope does), a side's innings for a `team_runs` line. `score_at` is the live body's own time (it can be up to about a minute behind `at`: the CDN holds it 15 s and may serve it stale for 45 s). A match the live scores do not list, or a failed live read, still logs the line, with the score columns null.
* **Match identity on every row** (self-contained rows): `match_key` (`<sorted team keys>@<kickoff>`, fixed by the match's first row; a later read of the same two sides with a start within 3 hours, or no start, is the same match), `home`, `away`, `league`, `kickoff`, `fmt`.
**Reading it.** Service key only (SQL editor or REST with the secret key). One line over time: `select at, over_price, under_price, runs, wkts, overs, b_runs, b_balls from inplay_log where match_key = '...' and line_key = '...' order by at`. A match's lines at a score: filter `match_key`, `inn_balls` between. Latest value per line of a match: `select distinct on (line_key) * from inplay_log where match_key = '...' order by line_key, at desc`.
**Volume.** See docs/OPERATIONS.md "In-play line log": the size estimate and what to watch on the free plan.
**Tests.** `site/tests/inplay-log.test.mjs` (change detection, returning lines, a book dropping out, failed and partial inserts, the read-back, score state for a T20 and a Test, the writer's calls against a mock database).

## 9. Gotchas and decisions (read before changing things)
* **No ball-level data in `data/`**: the CSVs hold per-player match totals only. Batting position, partnerships and fancy markets exist only because the site builder re-parses the Base zip.
* **A scraped match's event** takes Base's name for the same league (`base_event` / `league_key` in `build.py` / `crex_assets.py`; same gender, season and punctuation ignored, nothing guessed when two Base names share a key), so a live season sits with its history: the scrape's "Womens Big Bash League" is Base's "Women's Big Bash League", and its 2026 matches are that league's newest edition on the Leagues page. A league the scrape names with other words stays a separate event until Base publishes it.
* **A wrong photo or full name** is a hand-checked line in `data/mappings/player_identity.csv`, never another name rule (5.7). The automatic matcher takes "M Prasidh Krishna" for another Krishna whose first name starts with M, and a multi-initial history name ("RG Sharma", "JM Anderson") matches every source player with the same surname and first initial — two namesakes at equal strength leave a silhouette rather than keeping the sitemap's first pick. When the books name him exactly but the source lists that full name under several ids (three "Rohit Sharma" rows), a photo link that is not one of those ids is dropped and reviewed instead of silently keeping a namesake (Rydham for Rohit). Check a link on the source's player page (role, teams, age) before adding the line. `tests/site/test_identity.py` keeps each player and source id in the file once. The source sometimes stores initials as the given name ("ms dhoni"); `display_name` keeps those upper ("MS Dhoni").

* **Provisional matches** lack innings detail: they feed player props but not partnerships, position, innings order or match markets; filters drop them and say so.
* Player data sharded by `int(id,16) % 64`; partnerships live in the shard of the **lower** player index (pair lookups need only one shard).
* Home/away is **inferred** (tour name "X tour of Y", venue history, venue_geo country, majority host). Unknown hosts are excluded from home/away filters.
* `check_public_safe.py` fails on Vercel/Supabase hostnames in tracked files: pass URLs through repo variables, never write them in tracked files. Generated `sitemap.xml`/`robots.txt` are gitignored for that reason.
* YAML in workflows: an unquoted `: ` inside a `run:` one-liner breaks the whole file (GitHub reports only "workflow file issue"). Lint with `actionlint`.
* Cache key `site-dl6-<date>` in `site.yml`: bump the prefix when the format of cached downloads (e.g. `photos.json`) changes.
* macOS `sed -i` needs `''`; prefer Python for scripted edits.
* Vercel: `outputDirectory: public`; the SPA rewrite destination must be `/` (with `cleanUrls`, `/index.html` did not work). `.vercelignore` excludes tests/scripts.
* The Vite dev server has the SPA fallback built in, and serves `/api/ask` and `/api/live` with the same handlers Vercel runs (`vite.config.ts`).

### 5.11 Published hot rows (`site/packages/engine/hot-rows.js`, `site/scripts/hot-rows.mjs`, `hot-rows.json`)
**What.** The history half of every Hot props row (`HISTORY_FIELDS`: his player index and name, the line, the model's prior, the opponent and ground, the L5 / L10 / season / head-to-head / ground rates, the last ten bars, the settled value) for every priced pre-match line, built with the data and published beside it. A phone that reads it skips the player files (about 20 MB) and the scoring pass (6 to 7 s of JS on a phone) on a cold start; a line the file does not cover is scored on the phone as before.
**How.** `site.yml` runs `node site/scripts/hot-rows.mjs` after the data build and before the guard. The script runs the engine's `scoreLine` (the code the phone runs; `mobile/src/lib/hot.ts` calls the same function) over the priced pre-match lines of `value_bets/out/book_lines.json` (started within the keep window, or starting in the next 11 days) and writes `{ v, generated_at_utc, lines_generated_at_utc, build, lines, scored, skipped, rows }`; `rows` is keyed by `lineKey` (player, stat, format, match chip, innings scope, pre-match or live). The step fails soft (`continue-on-error`, the file is removed on failure): without it the apps score as before. It stays plaintext in `wrap.py` (the apps read it on a cold start). Guard check `h` (5.8) warns on a stale or malformed file.
**Rules.**
* **Only history is published.** The prices, books and quotes are the phone's own `book_lines.json` (fresher than the build), so a row is `rowOf({ line, books, history })`. `seedRow` uses a record only when its `line` is the one the books lead with now and, with the store loaded, when `idx` is still that player; otherwise the line is scored on the phone. Never store prices in the file.
* **Build-bound.** `idx` is a position in the build's player list, so the app reads the file only when `build` equals `meta.json`'s `built_at` (`hotRowsQuery`).
* **Same for everyone.** Nothing here depends on the viewer: `day` (the viewer's local day) is added by the reader, and live (in-play) lines are never in the file (the phone merges them from `/api/inplay`).
* **One definition.** A change to what a row holds is a change to `hot-rows.js` (the site's own hook `useHotRows` has its own loop and does not read the file yet).
